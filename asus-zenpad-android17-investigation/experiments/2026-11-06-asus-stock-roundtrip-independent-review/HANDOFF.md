**1. P1 operational blocker: mandatory `awk` is absent on the actual stock Android.**

Location: `../2026-11-06-asus-stock-roundtrip-continuation/source/service/transport.py:194` through line 210, inside `METADATA_GUARDS`.

The parent supplied a fresh, actual-device observation during completed factory preservation: `/system/bin/tar`, `stat`, `find`, `dd`, `readlink`, and `sha1sum` exist; `awk` and `sha256sum` do not, and `toybox sha256sum` reports Unknown command. This is parent evidence, not a reviewer device observation. The pinned helper successfully completed 39 file and six raw-partition captures, restored Enforcing, removed its temporary staging, and observed stock boot completion.

The new controller invokes `awk` nine times: cache mount count, mount source, filesystem type; battery voltage, presence, health, capacity and temperature; USB online state. The first invocation is in the mandatory preflight snapshot after private staging setup but before the para copy and before any candidate p10 write. With no `awk`, the equality check fails; the root envelope reports a nonzero operation status. No successful preflight or trial can result. A failed snapshot may leave that run's staging because this path does not execute normal snapshot cleanup; parent must inspect the typed result rather than assume cleanup.

Exact parent fix: replace all nine uses with Android `/system/bin/sh` builtin `read`/`case`/comparison parsing, or export bounded text through the existing checked channel and parse it on the host. Keep exactly-one `/cache` mount, canonical p24 source, ext4, absent command file, and every battery/USB threshold. Require every needed uevent key exactly once and reject missing, duplicate, malformed and nonnumeric values. Do not weaken a guard or introduce an unverified replacement binary. Add fixture tests that actually execute the generated parsing fragment against local text with `awk` unavailable; assert failure for duplicate mounts/keys, missing keys, wrong p24/filesystem and threshold failures. The current `SafetyTransport.root()` only records scripts, so its green result cannot test command availability or shell execution.

No device `sha256sum` replacement is necessary: whole-file and partition digest comparisons are performed on pulled bytes with host Python SHA256. The RC collector uses `tar -cf`, `wc -c`, standard shell arithmetic/globs and the existing staging operations. Parent evidence supports tar availability; live preflight still verifies its exact archive behavior and the inherited command options. This review did not establish an additional missing command.

**2. P1 correctness blocker: a failed or killed ADB entry process escapes the unknown-entry stop policy.**

Locations: `transport.py:51–60`; `controller.py:177–182`; `tests/service/test_faults.py`, `SafetyTests.test_entry_delivery_actual_adapter`.

`HostIO.entry()` returns `unknown` for raised timeout/I/O uncertainty, but every returned process result other than the exact service failure becomes `completion_unconfirmed`. That includes exit 1 with `error: closed` and signal exit -9. Those results do not establish completed service delivery. When a later new stock boot is observed, the controller permits TCP reenable and restoration for both cases. The task explicitly forbids those mutations after unknown entry delivery, even if new stock is subsequently seen.

Fresh review reproduction in `evidence/entry-error-boundaries.json` uses the actual adapter and actual Python controller/writer with fixture subprocess/storage effects. Both cases resulted in one TCP reenable call, `['candidate', 'stock']` writes, and `diagnostic_pass_stock_return_and_p10_restore_verified`. Through `main()` that outcome is an exit-0 outcome. Host command journals preserve the original status, but the controller classification defeats the required uncertainty rule. The existing adapter test explicitly expects `completion_unconfirmed` for rc=1/stderr=`closed`, so passing all 65 tests does not refute this issue.

Exact parent fix: retain the tightly recognized `reboot failed: -1` service response. Accept only the expected clean successful host completion as `completion_unconfirmed` (still requiring actual new stock boot before any inverse). Classify unrecognized nonzero/negative return codes and unexpected output/error shapes as `unknown`, retain stdout/stderr/exit status, and use the existing read-only observation/no-TCP/no-inverse branch. Do not retry entry. Change the existing rc=1 expectation and add integrated tests for closed transport, killed process, unexpected output, exact service failure, and clean completion; explicitly assert zero TCP calls and no stock inverse for unknown delivery even with a valid new-stock observation.

**3. P1 correctness blocker: review/window expiry is not enforced at mutation dispatch inside long phases.**

Locations: `controller.py:94–112`, `135–149`, `180–182`; `transport.py:61–78`, `88–101`; inherited `recovery_control.py:402–480`.

The outer review correctly checks source/evidence equality, literal true attestations, timestamps, the November 6 17:03–23:03 UTC authorization window, and the parent's shorter expiry. Checks occur before the install engine, entry preparation, TCP stage and explicit restore engine. The engine can nevertheless perform staging, multiple health/readback calls and a write after its last check. Its known-install-failure inverse has no review callback. The explicit restore engine likewise can finish after the last check and still report success. TCP has several reads between the outer check and its mutation, and no second check before connect.

Fresh `evidence/expiry-boundaries.json` advances a fixture authorization clock at three concrete boundaries without changing implementation:

- Expire during `install:stage_candidate`: the candidate write still occurs, then later refusal leaves the candidate installed.
- Expire at the completed candidate-write failure: the inherited engine still writes the stock inverse without a new review check.
- Expire during `restore:stage_stock`: the explicit stock write and subsequent guards complete, and the run reports the full success outcome.

These are dispatches initiated after expiry, not a demand to interrupt an already dispatched block write. The existing expiry test only fails the third outer callback after observation; it does not cover these gaps.

Exact parent fix: supply the existing review/deadline validator to the continuation transport and check it immediately before each new device command in writer/root/staging phases, including the inherited engine's automatic inverse, rather than only before `E.execute()`. Check directly before entry and each TCP mutation as well. Keep observation reads independently bounded; expiry must not request a reboot, inverse or retry. Ensure expiry refusal cannot enter an unguarded inherited recovery path. A dedicated terminal authorization-expired result is preferable to labelling expiry as transport uncertainty. Preserve verified readback facts and make unfinished cleanup/metadata explicit. Use an exclusive upper bound at expiry and retain parent admission margin for observation and restoration. Do not terminate an in-flight write merely because the clock crosses the deadline. Repeat the three reproductions and add expiry between TCP proof and dispatch, and before a root/staging command; assert no new mutation and no false all-success outcome.

The fixes can be confined to the continuation adapter/controller and tests; they need not weaken or replace the pinned p10 writer. New source pins must be generated and reviewed afterward. This reviewer made no implementation changes.
