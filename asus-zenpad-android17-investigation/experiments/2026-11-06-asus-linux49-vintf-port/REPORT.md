## What the actual source establishes

All paths below are relative to `source/`, which contains the exact read files and their hashed remote provenance in `evidence/*sources*.json`, `build-rules.json`, and `all-before-pins.json`. Current libvintf HEAD is `df89ad736e14ac375f61d50fa543ae7cd746a140`; kernel/configs HEAD is `200b3987b78fc25015bf826b281f0c3851daf146`.

- `system/libvintf/VintfObject.cpp:197`: a manifest with no level does **not** select a historical first-API-23 matrix. Framework matrix combination falls back to the minimum supplied numbered level, currently 7. Separately, framework-manifest filtering treats an unspecified device level as infinitely old (`:533`). Those two behaviors differ; the warning is not proof of a legacy kernel profile.
- `system/libvintf/VintfObject.cpp:996`: `checkDeprecation` rejects an unspecified Shipping FCM Version. Adding only a kernel entry would leave this independent failure.
- `system/libvintf/HalManifest.cpp:814`: from target FCM R/5 onward, kernel FCM is inferred from the manifest target unless explicitly supplied. Earlier targets can use unspecified kernel FCM and legacy matching.
- `system/libvintf/KernelInfo.cpp:76`: matching requires the same actual x.y, then the LTS/config predicates. There is no hard-coded universal `kernel >= 4.14` rule here. Unspecified kernel FCM uses the earliest matching profile and rejects a profile at R/5 or later without explicit kernel FCM (`:149`). Explicit kernel FCM at S/6 onward only accepts matching matrix KMI (`:111`). These rules are why a fake kernel version or arbitrary level assignment is unacceptable.
- `system/libvintf/CompatibilityMatrix.cpp:336`: framework fragments are combined by target/kernel FCM. Lowering target level can change HAL/deprecation selection. An additive port fragment can be loaded without replacing installed numbered matrices, but its level and kernel predicates must have a defensible meaning.
- `system/libvintf/AssembleVintf.cpp:559` merges explicitly supplied manifest levels; the vendor build in `build/soong/android/vintf_data.go:116` supplies device manifest files and sepolicy version. Neither implementation derives target FCM from first API 23. At target T/7 onward, AssembleVintf forbids explicitly setting kernel level (`AssembleVintf.cpp:541`, `constants-private.h:81`). Thus “target 7 plus explicit old kernel FCM” is not a valid minimal build-source fix.
- `system/libvintf/include/vintf/Level.h:39` names 0 as non-Treble LEGACY, 1 as O, 2 as O-MR1, etc. This alone does not establish a complete usable target-0 profile. AssembleVintf's enforced-VINTF comment at `:593` explicitly expects a non-LEGACY level; choosing 0 merely because the original device shipped at API 23 would require further support, not an invented empty level-0 matrix.
- `build/make/core/Makefile:5741` forwards `PRODUCT_SHIPPING_API_LEVEL` as `ro.product.first_api_level`. In the read production libvintf implementation it is not used to select/infer Shipping FCM. The schema VTS tests have historical first-API exceptions; these do not provide kernel requirements. The runtime property's separate vendor API derivation is visible in `system/core/init/property_service.cpp:1125`.
- `hardware/interfaces/compatibility_matrices/build/vintf_compatibility_matrix.go:203` supports device framework matrix additions and preserves the generated device matrix/sepolicy machinery. Standalone `vintf_compatibility_matrix` modules can also install `etc/vintf` fragments. This provides an integration mechanism, not provenance for a 4.9 profile.
