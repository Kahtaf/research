## Existing opcode 2 as future timing input

`source/rescue.c:118` already accepts opcode2 for original BOOT reconciliation (index1) with exact manifest digest and an externally authenticated full current recovery pin. It verifies identity, full current p10, the original SYSTEM prerequisite, all BOOT chunk hashes, then identity and full p10 again. An all-matching bitmap is required before treating the BOOT observation as original; the opcode itself can successfully reconcile a nonmatching BOOT without repairing it. **No opcode3 is required or used for this read-only observation.**

Its exact side effects matter: `recovery_pin` is assigned in daemon RAM before those checks; after successful checks it may remove a valid stale `/dev/rescue-state/journal.new` and fsync its RAM directory, obtains a random 32-byte token from urandom, sends token+bitmap, and sets that connection's state RECONCILED. It does not write SYSTEM/BOOT/recovery, publish journal VERIFIED/UNCERTAIN, or clear global frozen/uncertain state. Disconnect discards the connection token/state; an IDLE-only second reconciliation on the same RECONCILED connection refuses. Existing uncertainty restrictions still apply. At real daemon startup `serve` also clears stale pending publication under the writer lock, so the test's deliberately seeded pending file after setup models the reconciliation edge separately.
