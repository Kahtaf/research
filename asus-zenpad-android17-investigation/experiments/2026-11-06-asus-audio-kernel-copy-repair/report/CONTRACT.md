# Executed source contract audit

All kernel references below are exact independent copies from `/srv/android/asus-bmc156-full-kernel-r1/kernel`, checked against its physical BMC156 manifest. They are under `source/original/`; hashes are in `evidence/source-pins.json`. The older audio route ledger is evidence to correct, not authority over this source.

**The callback is status-only.** `sound/soc/soc-pcm.c:2812` installs the platform `.copy` directly; its pointer wrapper at1099 delegates to the platform pointer. `sound/core/pcm_lib.c:1997` and2219 implement the interleaved write/read transfer wrappers: channel=-1, position and length in **frames**, user pointer adjusted by the frame byte offset, callback result checked only for `<0`, and wrapper returns0 for every nonnegative result. The surrounding write/read loops release the PCM stream lock before transfer, reacquire it afterward, check negative result/state, and advance `appl_ptr`, user offset and xfer by **the entire requested chunk** (2096 and2328). They limit chunks at ALSA ring wrap. Callback return16 or256 is not a partial16/256-frame transfer.

`sound/core/pcm_lib.c:2119,2345` may return frames accepted by earlier successful chunks if a later chunk errors. That legitimate outer-loop short transfer differs from returning a positive value from this driver callback. The ioctl entrypoints in `pcm_native.c:2859,2939` export that result through `snd_xferi.result`; the captured SDK37 tinyalsa v2 `pcm_rw_transfer` at `source/contract/tinyalsa_new/src/pcm.c:1633` returns this result when ioctl succeeds. There is no tinyalsa64-byte requirement. The previous HAL's64-byte guard was a workaround for these driver defects, not an ALSA contract.

**Frames and storage width.** `pcm_native.c:566` derives `sample_bits` from `snd_pcm_format_physical_width(format)` and multiplies by negotiated channels for `frame_bits`. `include/sound/pcm.h:674,694` defines frame/byte conversion. `sound/core/pcm_misc.c` holds the physical-width table. A mono16-bit frame occupies2bytes, stereo16 occupies4; mono24-in32 or32 occupies4, stereo occupies8. Signedness/endian selection does not change container size. The inherited `audio_frame_to_bytes`/`audio_bytes_to_frame` in `mt_soc_pcm_common.c:18,38` special-case only S32_LE/U32_LE; other declared32-bit containers are incorrectly treated as16-bit. This patch uses the negotiated frame width for these two callbacks and pointers, leaving the shared legacy helpers and other PCMs untouched.

This establishes **transport byte geometry only**. It does not implement endian conversion or change AFE format programming. In particular, this is not evidence that all formats advertised by `SND_SOC_ADV_MT_FMTS` produce correct physical samples. Existing capabilities were neither broadened nor gratuitously narrowed. The minimal HAL's intended profile remains48kHz S16_LE, stereo speaker/mono capture, both unqualified.

**Alignment.** `pcm_native.c:3062` rejects byte reads that are not frame-aligned. `READI/WRITEI_FRAMES` already express whole frames. The AFE pointer/IRQ code observes progress in64-byte units; `Align64ByteSize` floors values. That hardware-observation granularity is retained. It is not a copy length requirement: `arch/arm64/kernel/io.c:26,56` implements byte heads,8-byte bodies, and byte tails for MMIO copies. The repaired callbacks copy every requested frame byte, including62/64/66 and60/64/68-byte boundaries. ALSA normally splits at ring end; the transfer helper also handles a wrapped request up to one ring without truncation. No physical timing/granularity claim is made.

**The I/O helper does not return a residual count.** `sound/core/memory.c:38,71` returns0 or `-EFAULT`. On this ARM64 build it uses256-byte stack chunks: capture reads MMIO then invokes `copy_to_user`; playback invokes `copy_from_user` then writes that successful chunk to MMIO. Underlying user-copy operations return bytes not copied (`arch/arm64/include/asm/uaccess.h`), which the helper converts into `-EFAULT`. An error can occur after earlier chunks or part of a capture user buffer have already changed. Error does not mean “nothing was physically copied.” The tests execute the exact non-i386/non-SPARC helper bodies, the same branch selected by ARM64, with user/MMIO boundaries substituted.

**Executed original failures.** `evidence/remote/evidence/host-tests.log` preserves negative reproductions from the exact original callback bodies: both callbacks accept68bytes after copying64; both accept128 with only64 available; DL1 rejects `access_ok` but still advances counters and returns0; UL1 user-copy failure returns0; zero-sized rings return0. On a fault in the second wrap span, original DL1 returns-1 after accounting64bytes; original UL1 returns256 after accounting64bytes, so ALSA accepts the entire128-byte request. Mono UL1 returns16 for32frames. That shifted result is erroneous status usage, not proof that the ALSA caller accepts only16frames.

**Concurrency.** `mt_soc_afe_control.c:3405,3603` updates DL1/VUL byte counts and hardware indices under each memory control's `substream_lock`, dropping it before `snd_pcm_period_elapsed`. The original PCM pointers instead take the separate `Auddrv_*_Spinlock` locks; original `.copy` takes yet another file-local lock. These do not mutually exclude IRQ accounting. `RemoveMemifSubStream:3033` clears the capture ring under `substream_lock`; DL1 stop originally called ClearMemBlock without it.

The repair uses stream lock then `substream_lock` for pointer sampling, MMIO snapshots and commit; IRQ still uses its original lock and order. A per-direction sleeping mutex serializes `.copy` with other copies and with the platform's buffer setup/free operations. The streaming stop path never waits for that mutex: its generation increment invalidates a user copy in flight, and DL1 reset now uses the IRQ ring lock. User copies/allocation/free occur outside both spinlocks. Normal DMA producer/consumer deltas are retained; updates use the current count under the shared lock, not a stale count snapshot.

Playback first copies the complete request to a bounded temporary buffer; a user fault cannot modify its DMA target. Capture snapshots kernel/MMIO bytes before copying to userspace. After user access, state, stop generation, buffer identity/geometry, application-side index, and whole-request availability are revalidated; running hardware position is refreshed. Only successful complete requests move application indices/counts. Capture may have modified part or all of userspace before a fault or post-copy xrun error, but those bytes are not reported accepted and the callback does not consume them. Real hardware-progress counters may still change independently.

**Limits.** These are not DMA hardware or scheduler proofs. Modulo hardware pointers cannot expose arbitrary completely missed ring laps; IRQ pacing and real overrun/underrun behavior still require hardware qualification. Kernel-to-MMIO staging copies under the ring lock are bounded by the existing platform maximum (48KiB); their worst-case IRQ latency and allocation behavior have not been measured on MT8163. MMAP, silence callbacks, other PCM devices, malicious concurrent ALSA lifecycle use outside this driver, codec/AFE format correctness and analog routing are not qualified by this patch.
