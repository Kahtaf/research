# Source conclusion

**Prefer one read of `/proc/aed/reboot-reason` now. Its LAST PC section uses the snapshot captured during this stock boot.** It does not establish that the snapshot belongs to Linux 4.9. The sysfs `lastpc_dump` endpoint instead rereads hardware registers at read time; a single read is reasonable as a passive diagnostic without another reboot, but its capture epoch and hardware retention are unproven.

## What the code does

1. MT8163 platform `arch_initcall(lastpc_init)` installs its operations and a 2048-byte minimum buffer. Common `module_init(lastpc_init)` calls a no-op platform `start`, registers the platform driver, maps DT resource 0 in `lastpc_probe`, creates attributes, allocates `lastpc_dump_buf`, and calls `lastpc_dump` once into that buffer (stock `lastpc.c:233–264`). The cache is a current-stock-boot initialization snapshot, not the old printk buffer or a timestamped firmware record. There is no subsequent cache update in the inspected driver.
2. Reading `/sys/bus/platform/drivers/lastpc/lastpc_dump` calls `lastpc_dump_show`, directly invoking `plt->ops->dump`; it bypasses `lastpc_dump_buf` (`lastpc.c:166–175`). The shipped binary corroborates the indirect callback and the separate cache-copy function.
3. MT8163 dump reads PC/FP/SP from mapped MCUCFG base plus `0x410 + 0x20*(cpu%4) + 0x100*(cpu/4)`. ARM64 reads PC high/low at `+4/+0`, FP at `+0x14/+0x10`, SP at `+0x1c/+0x18`, combining 32-bit halves. With compiled DT base `0x10200000`, core 0 PC comes from `0x10200414/0x10200410`. It reads the possible CPUs sequentially; no coherent all-core capture is requested.
4. The active MT8163 dump path contains register loads, formatting, `kallsyms_lookup`, and `pr_err` logging. It contains no latch-control store, clear, rearm, CPU-debug enable, or sampling trigger. The commented mux-write block is disabled. `start` is a no-op. This is **read-time access to hardware latch registers**, not proof of live CPU instruction sampling. Opening sysfs does produce kernel log lines; it is not entirely without observable software effects.
5. The stock cache comment explicitly says it prevents values being cleaned by low-power mechanisms when MCUSYS turns off (`lastpc.c:262–264`). Thus later sysfs reads may differ or be zero. Kconfig describes the intended crash/shutdown latch surviving a reboot, but provides no reset-class, bootloader, watchdog, secure-firmware, or read-to-clear contract. These sources do not establish when the silicon captures/rearms/overwrites the latch or whether intervening firmware/reset/stock execution already replaced it. No blanket previous-reset guarantee follows. The 4.9 counterpart preserves these cache/sysfs semantics and adds another direct register-reading helper; it does not supply the missing hardware retention contract.

## Cached accessible interface

`/proc/aed/reboot-reason` is mode 0444: `aed-main.c:1984` creates `/proc/aed`; `aee/common/reboot-reason.c:64–68` creates `reboot-reason`; its `single_open` uses `aee_rr_reboot_reason_show`. The RAM-console implementation iterates `aee_rr_show[]`, including `aee_rr_show_last_pc`, which calls `mt_reg_dump`. That function only copies the already formatted `lastpc_dump_buf`. The adjacent LAST BUS provider also copies its own cache. No LASTPC register reread is performed by this route.

The shipped binary corroborates `aee_rr_show_last_pc -> mt_reg_dump -> strlen/strncpy`, boot cache population, and a compiled callback-array prefix ending in `aee_rr_show_last_pc` at `0xffffffc001002ca0`. Runtime availability/read permission for this proc path has not been observed in this task. The handler first validates old RAM-console data; `NO VALID DATA` can suppress the LAST PC output. Missing output is inconclusive. This interface is distinct from `/proc/last_kmsg`; do not assume the already captured printk text contains this proc-generated section.

## Interpretation and next action

**One concrete next action:** Parent reads `/proc/aed/reboot-reason` once through its existing USB path and preserves the full returned report with the already established stock boot ID `07b983d4-92fd-4abd-ad7f-4afb6e017571`. This task did not read the device. No additional reboot is needed. If unavailable, the qualified fallback is one read of the already observed sysfs `lastpc_dump` endpoint; no activation is required by this driver. Its read path has no explicit hardware write, although source alone cannot exclude undocumented hardware read side effects.

For either route, use the numeric PC/FP/SP values as candidates only. The driver calls **the current stock kernel's** `kallsyms_lookup` and does not verify that the address came from this kernel; a retained 4.9 address overlapping stock text can receive an entirely wrong stock function name. It ignores lookup failure as well, so failed lookup text is not reliable. Resolve against the exact candidate 4.9 symbol map only if independent evidence supports that origin, accounting for its actual load/relocation. A stock-looking name proves neither stock execution nor a 4.9 failure site. Nonzero values show what the register/cache held, not which boot produced it; zeros/absence do not prove nonexecution. This investigation provides no evidence justifying another flash.
