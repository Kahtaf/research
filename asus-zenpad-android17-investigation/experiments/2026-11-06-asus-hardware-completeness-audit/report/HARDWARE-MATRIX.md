# P00A_2 hardware completeness — 2026-11-06

The staged SDK37 product is **not yet a usable-hardware product**. Audio, camera and sensors lack device HAL packaging/declarations in the original full candidate, active r5, continuation product, and combined integration-r5 product. Camera and sensors also have concrete kernel gaps. These do **not** need to block a separately qualified experimental RAM kernel/early-init probe; they do prevent a claim of usable Android17 hardware. No physical Linux4.9 result exists in this audit.

Before userdata destruction, the two radio files are **insufficient evidence that factory calibration is preserved**. Public stock code identifies additional userdata records and a separate `/persist` filesystem. Follow the [private preservation checklist][C] before destructive work; this audit accessed none of those actual values.

## Integration contract and order

1. **Preserve factory state first** using the separate checklist. Do not run a legacy NVRAM daemon against missing files: its library contains restoration/default-generation and write paths. Public defaults are not per-unit backups.
2. **Keep the original live r5 frozen.** This audit neither polled nor managed that build. Parent owns the build lock, integration and physical gates. No elapsed-time inference establishes user presence or physical GO.
3. For the first RAM/early-init milestone, retain the already accepted rescue, memory, USB, charging-disabled and kernel gates. Optional camera, compass, audio effects, CTS and Play certification are not prerequisites for that diagnostic. A useful interactive OS additionally needs demonstrated display/input, storage and stable framework behavior.
4. Next hardware source work should be **one bounded audio route audit and one bounded accelerometer ABI port**, serialized or separately owned by the parent. This is a staging recommendation, not authorization for this research task to compile or integrate. Parent can defer cameras while qualifying the basic tablet.
5. For each future HAL stage, match service binary architecture to all in-process dependencies. ARM64 system_server can call an ARM32 binder HAL, but ARM32 blobs cannot load into an ARM64 process. Current BoardConfig supports both. Keep current Bionic/libbinder; do not replace system libraries with Android7 ones to satisfy a blob. Prove every undefined symbol and linker namespace dependency before running it.
6. Init and policy are part of each stage: upstream audio service runs as `audioserver`, sensor service as `system`, camera provider as `cameraserver`. Existing platform labels cover `/dev/snd/*` (`audio_device`) and `/dev/input/*` (`input_device`); they do **not** supply every MTK sensor/camera sysfs, ioctl or calibration permission. Add narrowly scoped vendor types, actual physical sysfs `genfscon` paths, per-domain ioctl allowances and private calibration locations. Device permissions alone do not grant SELinux access. No broad permissive mode, root HAL or blanket `/data/nvram` access. [S9][S10]
7. Assemble VINTF with **only installed, runnable services**, and run the full product's real `checkvintf`, ELF, init and SELinux checks after parent integration. Old shipping API23 does not itself prove every legacy HAL is accepted. Feature XML must reflect implemented hardware; a null audio/camera/sensor service is not completion.

No claim is made about actual saved calibration completeness, successful 4.9 boot, audio/camera/sensor operation, root availability, Google Play/Services runtime, certification or hardware suspend behavior.
