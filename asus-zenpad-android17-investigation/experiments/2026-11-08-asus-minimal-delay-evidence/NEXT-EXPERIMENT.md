# One delay-primitive fail-stop diagnostic

Decision: prepare one exact minimal-platform descendant with a diagnostic iteration ceiling inside __delay. Normal return and read/comparison/YIELD semantics remain unchanged. Exhaustion must panic rather than return early. The existing config's CONFIG_PANIC_TIMEOUT=1 is preserved, without promising physical automatic reboot.

Evidence: exact cached PC maps to __delay+0x44, the workaround-key comparison. Its capture epoch is not established. Earlier selected CNTPCT exposure completed one selected delay but did not qualify later ADC/PID1 progress; it did not change the shared primitive. The reduced-consumer run reached normal-priority PID1 and retained compute-begin plus two later deferred-probe messages, but no compute-end/timer stage. These support one diagnostic lead rather than a cause.

Opus 5.5 was consulted first and declined to finish its design. Exact Large v2 was then confirmed. Parent accepts its suggestion to test the shared primitive but rejects early return, uncalibrated iteration-to-seconds claims, global counter-root-cause conclusions, and treating missing exhaustion as a negative. A diagnostic ceiling can catch a legitimate long delay too; caller and requested/observed cycles must be interpreted.

Change scope: one __delay counter/terminal panic guard; only necessary fresh run identity and package metadata elsewhere. Preserve minimal config/DT hardware statuses/bootargs/helper/ramdisk/protection and charging inhibition. No clock-route change, driver removals or per-subsystem instrumentation. One build, focused binary/packaging checks and one real parent-owned recovery trial after review. No device operations by implementation worker.

Suggested ceiling: 16,777,216 completed continuing loop iterations. This is an instruction-count diagnostic threshold, not a walltime bound. Worker must verify call/conversion context and flag any direct legitimate requirement incompatible with it before building. Keep original starting read and exactly one original-route condition read per loop, original unsigned subtraction/comparison and YIELD. On exhaustion, report fresh identity, requested cycles, original start and last condition counter values, completed iterations and caller PC through one terminal panic message/backtrace. Do not add a new clock read or log each loop. If panic/retention cannot publish, UNKNOWN.

Outcomes: fresh matching exhaustion+caller localizes one delay that exceeded the budget in that exposure; returned counter values characterize that observation, not all timekeeping. No completion after it is expected from a fail-stop. Compute-end and all five timer pairs plus verified stock return, without exhaustion, establish bounded minimal liveness under the diagnostic perturbation; no shipping or exclusive-cause claim. Partial/no diagnostic, loss or ambiguous identity remains UNKNOWN and stops. It cannot rule out read-instruction stalls, repeated short calls, scheduler starvation or a different obstacle.

One physical trial only, then reassess. Experiment 3 remains open until its actual liveness criteria pass. No Android17 flash or BOOT/SYSTEM/DATA write follows from a delay diagnostic alone.
