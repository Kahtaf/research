## Findings requiring parent action

### R1 — P2: a visible DONE receipt can coexist with a failed publication and live UNKNOWN

**Reproduced with the actual production host and session/core implementation.** `source/host.py:27` renames `receipt.json.new` to `receipt.json` before directory fsync at line 28. If that fsync fails, `_exchange()` returns `UnknownOutcome` and attempts to replace the visible success receipt with UNKNOWN (lines 84–89). That rewrite is best effort and can also fail.

The independent test injects an I/O error at fsync number four, the final directory sync after a successful rename, followed by unavailable storage for the UNKNOWN rewrite. Results:

- Target: DONE, one writable open, 16 writes, second attempt refused.
- Host API: UNKNOWN.
- Durable initial `attempt.json`: UNKNOWN.
- Visible `receipt.json`: DONE; final directory-entry durability was not established.

Evidence: [receipt-edges.json](linux-results/evidence/receipt-edges.json), [exact visible receipt](linux-results/evidence/receipt-edge-visible-final.json), [test](scripts/receipt_edges.py). This does **not** demonstrate a false device readback: the target really finished and the host verified its final hash. It demonstrates ambiguity between observed device completion, durable publication, and the host's accepted terminal outcome. The supplied five durability cases fail earlier, before rename, and do not cover this edge.

**Smallest parent fix:** make a live `UnknownOutcome` authoritative in the parent supervisor and document that discovering `receipt.json` alone cannot override a known failed publication. Define the replay rule for conflicting/ambiguous records before integrating this host. Retain the initial UNKNOWN attempt and treat an unaccepted success file as device-result evidence, not permission to reboot/reset or retry. Require the successful return from the publication path for immediate downstream acceptance. On interrupted/ambiguous sessions, retain UNKNOWN and use separately authorized read-only observation; do not retroactively turn a lost receipt into success. Add the post-rename directory-fsync/storage-loss regression to the parent implementation. Do not claim that writing another local marker can guarantee recovery when that same storage is failing.

No target writer change or weakened guard is needed for this correction.

### R2 — P1 qualification gate: the effective silent-phase limit is 15 seconds, not 300

`source/host.py:42–52` sets an overall 300-second deadline but caps **every socket receive** at 15 seconds. The first reply, 0xb0, is sent only after `handoff.h:4` verifies original SYSTEM and BOOT, exec occurs, and `p10_restore.c:86` verifies the same pair again.

That first silent phase reads and hashes **7,541,284,864 bytes**: twice 3,753,902,080-byte SYSTEM plus twice 16,740,352-byte BOOT. Finishing within 15 seconds requires over **502,752,324 bytes/second aggregate read-and-hash throughput**, before identity checks, exec and other overhead. This is arithmetic from production source, **not a claim about measured tablet speed**. No such large read was run during this review.

The actual production host, against an explicit delayed-response model, returns UNKNOWN with only opcode 0x30 sent when a valid first acknowledgement would take 16 seconds. Evidence: [timeout-model.json](evidence/timeout-model.json), [model](scripts/timeout_model.py). This model does not benchmark hardware. The post-activation reply is also silent while the target writes, fsyncs and performs 19 full p10 scans; that phase needs its own budget. A timeout does not stop target block I/O. A failed handoff may also have consumed the old RSC daemon through exec, so an initial timeout is not a harmless permission to reconnect/retry.

**Smallest parent fix:** establish bounded phase timings during separately authorized read-only STOCK commissioning and give the initial proof and final write/readback responses explicit phase budgets under a hard operation deadline. Alternatively demonstrate that the unchanged 15-second limits cover those phases with adequate margin. Add delayed-valid-response tests. Preserve both original-pair proofs, all p10 transition scans, and terminal UNKNOWN behavior; do not solve this by caching away checks or retrying after timeout. This timing gate must be resolved before relying on the terminal operation as the rollback route, but it does not require a successful physical restore before an offline STOCK-only build can be reviewed.

## Independent implementation assessment

**Source, preload and memory.** `host._payload()` reads one fixed regular-file descriptor, rejects a final symlink, and verifies all original bytes before any request. Target staging accepts only the fixed next chunk length, 16 chunks total, into anonymous RAM. `restore_prepare()` hashes the complete payload against a compiled original hash, applies read-only protection, and hashes it again. `restore_run()` hashes it once more before opening writable. The production writable adapter is reached only after those steps and a full actual preimage check. Independent instrumentation asserted complete staging, the correct full hash, a sealed buffer, and UNKNOWN state at every writable-open entry. Mutation during sealing was rejected before an open. The payload, preimage and scratch mappings total **34,529,280 bytes**, excluding executable/self mapping, globals, stack and other process costs. Swap must be absent and is rechecked in target guards. This is a bounded-memory assessment, not physical OOM qualification or cryptographic protection against a hostile kernel.

**Fixed target and identity.** The only new write open is the literal `/dev/block/mmcblk0p10`, with `O_RDWR|O_EXCL|O_DIRECT|O_NOFOLLOW|O_CLOEXEC`. Production validation requires recovery alias `/dev/block/platform/mtk-msdc.0/11230000.MSDC0/by-name/recovery`, 179:10, start 160184, 32696 sectors, 16,740,352 bytes, root:root/0600, exact recovery label, held-FD/path/alias identity, empty holders and no major179 mounts. CID digest, both GPT hashes and Enforcing are repeatedly checked. No request supplies a path, offset, source hash, target partition or override. No discard/erase/TRIM ioctl, p20 write or other new block writer appears. The helper policy allows only BLKGETSIZE64 on four read targets and write on the recovery type alone. Hardware descriptor/alias/claim behavior remains a separate physical gate.

**Preimage binding and external trust.** The target pins normalized header, wrapped stock kernel, MTK wrapper and the padded compressed core, then checks canonical helper archive metadata/content against the RAM filesystem helper file, Android ID, and all trailing padding. The host separately compares the actual full prior digest to its fixed final-image pin. A test changing both the simulated trusted helper bytes and the matching capsule, with a recomputed Android ID, passes the structural predicate but changes the full image digest. Changing only the disk capsule while retaining the trusted helper is refused. This exactly demonstrates the declared boundary: helper equality is not helper self-authentication. Parent authentication of the entire deployed image/helper plus the fixed host pin is indispensable. No claim against hostile privileged RAM/kernel is justified or needed. Under that boundary, the current p10 bytes are checked, not assumed immutable from an earlier cached pin.

**Write, readback and terminal truth.** Before writing, actual p10 must equal the admitted full preimage; the check is repeated after the exclusive writable open. A post-open mutation test stops with zero writes. Each fixed sequential write is followed by fsync and a full comparison against the verified original prefix plus the captured preimage suffix. Final success requires an additional fsync, closing the writable descriptor, reopening read-only, a complete actual scan, guards and the exact original digest. Success reads **334,807,040 p10 bytes** across prepare/run. All 16 possible partial-write positions and all 17 fsync failure positions remain UNKNOWN, never DONE, with no second attempt. SKIP requires a full actual stock read and zero writable opens. A target DONE with a lost host commit receipt remains host UNKNOWN. Terminal status/read-only observation cannot restart staging or ordinary RSC.

**RSC transition and serialization.** The original source diff contains only the optional handoff include, opcode admission and descriptor capture; existing per-chunk recovery hashing and ordinary RSC guards remain unchanged. The ordinary writer cannot write p10. New opcode 0x30 requires connection IDLE, two records, no uncertain transaction, identity and both full original images. The helper additionally requires the exact original two-role manifest. Saved copies of the accepted socket, lifetime lock and listener are remapped to 3/4/5 without CLOEXEC. Remap/exec failure after remapping begins exits instead of returning to the daemon. Eleven new small-file fixture cases check IDLE admission; zero/four/five-role refusal; changed SYSTEM/BOOT refusal; RECONCILED/WRITING/VERIFIED refusal; refusal after uncertain disconnect; and exit74 on a remap failure. At the intercepted exec boundary, actual inherited descriptors and exclusive bind ownership were checked. The fixture uses a private review lock name and intercepts exec; it is not a production-name, root/peer or SELinux transition qualification.

**Policy, peer and executable surface.** Fresh 72 checks include 29 actual compiled-context lookups. Block-mode rules retain `-b`; symlink and regular-file lookups retain their proper stock types. The policy delta preserves original AV rules, constraints and permissive map. New helper types inherit no broad attributes; the helper has one block writer, no userdata/default metadata access, no mount/setenforce/reboot grant, and no permission to execute an ordinary shell. Entry requires root, exact helper domain, Enforcing, UID2000/shell peer and inherited lock. `/system/bin/sh` is the exact fixed rescue proxy, also present at `/sbin/rescue-proxy`; its source accepts the fixed non-PTY `rescue-v1` route or the fixed adbd launch route, not arbitrary commands. No ordinary shell was added. Static policy permission queries do not establish real labels, authenticated USB, inherited-socket behavior across real exec, or OEM kernel enforcement; none is reported as physical readiness.
