# Fitted OV5670/OV2680 public-source evidence unit

Completed: a reproducible pinned-source extractor and host witness execute **34 unchanged production functions** across **93 cases** (48 OV5670, 45 OV2680). Twelve focused tests pass. This supplies actual source-mode facts for later metadata work. It supplies no HAL3 characteristics, templates, capability/version properties, Android streams or hardware qualification.

Only this new spike was written. No device, ADB, root, SSH, cloud, live sensor, OTP/private calibration, vendor binary execution, external communication, active AOSP/kernel/product/probe edits or camera operation occurred. Cached parent selection remains main `ov5670mipiraw` / sub `ov2680mipiraw`; logical IDs, facing and orientation are unqualified. OV2680B was not used. The Android11 HAL1 Echo Show donor and its shelved DpIspStream adapter were not used.

## Reproduction and outputs

From this directory run:

```sh
python3 scripts/run.py
```

Python standard library and installed clang suffice; no packages, downloads, kernel build or vendor dependencies. The runner rechecks the parent's four pins before extraction and after execution, preserves failing compiler/linker receipts, and runs the behavioral tests. Golden complete-program trace hashes live in `tests/expected-programs.json` and are **not** regenerated by the runner.

- `evidence/sensor-facts.json`: compact machine-readable ledger. Per-sensor source/hash context, exact declaration lines, winsize row hashes, valid/unknown register bytes, rational derivations, scenario comparisons, setter witnesses and limitations. Pretty-print with `python3 -m json.tool evidence/sensor-facts.json`.
- `evidence/exact-source-receipts.json` and `extraction.json`: four whole-file pins; exact function bytes, SHA256 and inclusive line ranges; audited call/state dependencies; crop dispatch receipts; pinned winsize type and kernel COPYING.
- `generated/*-production.inc` and `*-<function>.inc`: unchanged extracted bodies. `#line` directives give every recorded write its actual original source line. `*-host.c` and `tests/host-fixtures.h` are explicitly synthetic host glue.
- `evidence/{ov5670,ov2680}-traces.json`: complete ordered writes for every case, source line/function, software state and stage boundary. `*-compile.json`, `*-link.json`, `*-run.json`, `*-binary-audit.json`, `toolchain.json`, `tests.json` and `artifact-pins.json` retain execution/check evidence.
- `evidence/metadata-input-coverage.json`: eight SDK37 characteristic/request categories and all six template categories, with actual header token lines/hashes and explicit missing inputs. No contract values are emitted.

## Exact source and execution boundary

The parent's `2026-11-06-asus-camera-metadata-source-inputs/evidence/asus-sensor-source-pins.json` pins the four OEM files under `2026-11-05-asus-latest-android-feasibility/sources/asus-original/kernel-3.18/drivers/misc/mediatek/imgsensor/src/mt8163/`. All four are copied verbatim under `inputs/`, retaining their notices. `inputs/COPYING.kernel` retains the source tree's license text; it does not invent a new per-file license. The pinned OEM winsize struct at `kd_imgsensor_define.h:651–668` establishes the ordered stage-field names. No source tree or nested repository was modified.

The extractor audits calls before compiling. The whitelist contains mode-setting bodies, scenario wrappers/control, `set_dummy`, `set_max_framerate`, `set_max_framerate_by_scenario`, legacy `set_video_mode`, and `get_default_framerate_by_scenario`. OV5670 custom1 is included. Functions may call only those whitelisted functions or the explicit write/log/delay/lock fixtures. Unreviewed calls, preprocessor branches and pointer-member dereferences fail extraction; full-source pins independently reject any changed source.

`write_cmos_sensor` is replaced at the call boundary by a recorder macro/function that saves address, byte, caller source line and function. Bodies remain byte-for-byte identical. Unlike an actual write, it cannot touch I2C. LOG_INF, LOG_DBG, mdelay and spin locks are explicit no-ops. Fixture enum/status numbers are symbolic test labels, not numeric OEM ABI evidence. Every case starts with zeroed **host software state** and an empty, invalid register map; caller FPS is a fixture input, not a physical default. Tests also retain write history across preview/high-speed transitions.

Mode/state typedefs are extracted unchanged from the pinned sensor headers, preserving the OEM integer field widths. The narrow info container uses those exact mode types and the original mode initializers; unused info fields are omitted. Scalar aliases and enum labels are explicit host fixtures, with no layout/ABI claim. A separate 32-bit default-query sentinel cannot widen or truncate the OEM 16-bit current_fps field. Final review corrected an earlier widened fixture; old traces and the resulting golden-test failure are retained. All 93 ordered register programs and non-query states were compared and proved unchanged before the observation-schema golden was updated (`fixture-type-review.json`).

No sensor-init/default subset is needed to demonstrate these output/timing writes, so none is executed. No `open`, probe, sensor-ID read, shutter/gain, feature_control, debugfs/proc, OTP or calibration function is compiled into the witness. Feature-control crop dispatch is extracted as text evidence only. Binary import audits contain only stdout/abort and UBSan support, with the host system/UBSan runtime libraries. The production whitelist has no file-opening, socket, sensor-read, hardware transport or vendor-library call. Loader activity and stdout are ordinary host runtime activity; this is not an OS-sandbox or hardware-emulation claim.

Compilation is sequential, ordinary non-LTO single-frontend C, followed by Apple's installed serial classic linker. `-Wall -Wextra -Werror` applies, with only unused fixture parameters exempted. UBSan runs with recovery disabled. A 30-second CPU-time limit and zero core limit apply. Darwin rejects AS/RSS/DATA rlimits; the retained failure explains this limitation. `/usr/bin/time -l` records observed peak RSS and the runner requires it below 1 GiB. Successful compiler peaks were approximately **82 MB / 65 MB**, well below budget; this is observed usage, not a hard memory cap or CPU-affinity claim. Classic ld's deprecation warning is retained. ASan shadow reservation is unsuitable for a small address-space budget and was not used.

## Actual geometry and timing

The following are sensor-register output dimensions, not Android streams. HTS/VTS are complete 16-bit pairs assembled from recorded 0x380c–0x380f bytes. Declared pclk is a source clock input, not a measured or independently PLL-decoded clock. Exact rational arithmetic is used throughout the ledger; nominal `max_framerate` remains in tenths.

| Sensor / source mode | Programmed output | OEM grab window | HTS × VTS | Declared pclk / (HTS × VTS), Hz | max_framerate, tenths |
|---|---:|---:|---:|---:|---:|
| OV5670 pre / normal_video / slim_video / custom1 | 1296×972 | 1280×960 | 1676×2045 | 5142500/171371 | 300 |
| OV5670 cap, FPS other than 150 | 2592×1944 | 2560×1920 | 1676×2045 | 5142500/171371 | 300 |
| OV5670 cap1, FPS = 150 | 2592×1944 | 2560×1920 | 3352×2045 | 2571250/171371 | 150 |
| OV5670 hs_video | 644×480 | 640×480 | 1676×511 | 25712500/214109 | 1200 |
| OV2680 pre / cap / normal_video / slim_video | 1600×1200 | 1600×1200 | 1700×1294 | 330000/10999 | 300 |
| OV2680 cap1, FPS = 240 | 1600×1200 | 1600×1200 | 1700×1294 | 330000/10999 | 240 |
| OV2680 hs_video | 1280×720 | 1280×720 | 1446×760 | 275000/4579 | 600 |

For all listed scenarios, programmed HTS/VTS agree with the selected imgsensor_info structure. Programmed output agrees with winsize stage `w1_size/h1_size`; the final `w2_tg_size/h2_tg_size` agrees with the grab-window declaration. Those equalities are tested separately and do not establish the transformation, effective Bayer origin, active-array rectangle or ISP output.

OV5670 mode bodies (`preview_setting:906–959`, `capture_setting:961–1053`, video/high-speed/slim/custom1 receipts in extraction.json) never write 0x3800–0x3807. All crop starts/ends remain unknown in this unit. OV2680 preview (`492–539`) and high-speed (`652–699`) write start **low** bytes 0x3801/0x3803 but omit 0x3800/0x3802. Thus even its start pairs are unknown; assigning high bytes zero would invent initialization state. OV2680 known end pairs are 1615/1215 for preview and 1455/973 for high-speed. Raw end values and winsize fields are preserved without interpreting them as inclusive active-array dimensions. Mode transitions cannot supply the missing high bytes because neither whitelisted mode writes them.

## Branch and setter findings

OV5670 capture has the real predicate `currefps == 150`. It writes HTS 3352 and PLL-related 0x0303=1 on that side, versus HTS 1676 and 0x0303=0 otherwise. Tests exercise 149/150/151, 239/240/241, nominal 300, zero and 65535. Preview/normal/slim/custom1 output is 1296×972 despite smaller grab dimensions; high-speed writes **644**, not 640. Source comments about generic PIP 24 fps and mode-rate headings are not treated as behavior.

OV2680 `capture` selects cap1 software declarations when current_fps=240 (`929–954`), but `capture_setting:641–645` calls the unchanged `preview_setting` without a rate branch. Video and slim do the same. All tested capture FPS values produce the same register program. Its cap1 240-tenths declaration therefore does not by itself mean capture applies 24 fps, and the nominal base-ratio difference is not evidence of a hardware contradiction.

Actual timing setter execution resolves the important distinction:

| OV2680 tested sequence, current_fps=240 | Software frame_length after call | Recorded VTS | New register writes |
|---|---:|---:|---:|
| capture only | 1294 | 1294 | 38 |
| capture → set_max_framerate_by_scenario(capture,240) | 1617 | 1294 | 0 after capture |
| capture → legacy set_video_mode(240) | 1617 | 1617 | 4 after capture |

Production arithmetic is integer `pclk / framerate * 10 / linelength`; it gives 1617 for OV2680 at 240 tenths. The scenario setter's `set_dummy()` calls are commented out (`1209–1286`), so this path changes software state only. The legacy setter calls `set_max_framerate` → `set_dummy`, which writes VTS/HTS; its exact source-clock ratio then is 220000/9163 Hz, separately from nominal 24. Source `set_video_mode` is itself commented “not used after ROME”; this fixture does **not** prove that any active HAL invokes it. OV5670 scenario setters likewise update state without register writes; at 240 tenths, state becomes VTS 2556 while registers retain 2045 unless the tested writing path runs.

Small exact-ratio differences from nominal 30/60/120 or 15 may reflect source-clock rounding. PLL/default dependencies and exposure/flicker timing prevent treating these arithmetic ratios as measured delivery rates. Tests retain flicker 300→296 and 150→146, dynamic-zero no-op, min-frame/clamp behavior and positive-rate preconditions. Zero is tested only where production guards it; unguarded division-by-zero paths are identified by source and never invoked.

OV5670 custom1 is a concrete incomplete mapping: `control:1807–1839` calls custom1, but `SENSOR_FEATURE_GET_CROP_INFO:2085–2106` has no custom1 case, so default returns winsize row 0 rather than declared row 5. The two rows happen to contain identical numbers today; this is an incomplete dispatch, not a present geometry contradiction. `get_default_framerate_by_scenario` also has no custom1 case, leaving a host sentinel untouched; `set_max_framerate_by_scenario` falls back to preview arithmetic. The ledger flags both omissions rather than inventing a custom1 crop/default-rate contract.
