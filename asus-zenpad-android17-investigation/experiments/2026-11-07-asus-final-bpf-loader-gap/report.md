# Exact cause and next fix

**The first fatal is a missing virtual-kernel metadata syscall, not an incorrect ARRAY declaration or evidence of a product-loader bug.** The completed final Android boot used Image SHA256 `95a62a8bccd3085d682a89b6c74c7afd0961cebd1e3137b256229849920b549b`, config `c2ea1277e1574da39d1d55d31bde7bda439ab624561ad3c6a6f4730e38f57834`. That kernel does not implement `BPF_OBJ_GET_INFO_BY_FD` (15).

The actual boot completed odsign/ART and activated 39 APEX packages. At guest 383.008292 seconds NetBpfLoad reported all five found fields as `-1`, errno22; `offload.o` returned `-76` (`ENOTUNIQ`). The real bpfloader service exited38 at 403.023 seconds and init honored its `reboot_on_failure`. These are a metadata-query failure and a genuine fatal boot boundary; the log does not establish that the map's actual attributes differ.

## Three checks establish the cause

1. **Final installed bytes.** Read-only `debugfs` extraction of the small Tethering CAPEX from the existing `fff09d5a…` raw, followed by EROFS extraction inside this spike, yielded `offload.o` SHA256 `4ed894d5ae7d49caf9cb54b22d010eb7a7672fc68e634ed1163d28cb7bfd3198` and NetBpfLoad `2bf5e22c967a3e2ab38ef0699056616346fd3dceae230f5950e9f4de82839985`. Both match the published final-byte network qualification. `tether_error_map_def` is the first 192-byte entry in ELF section `.android_maps`; its first five u32 values are exactly `2,4,4,31,0`. The raw remained inode28131263, 3753902080 bytes, mode0444, with unchanged mtime. The published final-report hash was verified; no full raw hash or copy was performed.
2. **Actual kernel implementation and binary.** The selected Image and config match `asus-firstboot-runtime/kernel-build-r7`. Its source `kernel-cpuset-r1/kernel/bpf/syscall.c` is the unpatched baseline hash `4633a05b…`; the UAPI header is baseline `0acaebd9…`. Both lack command15. The linked `SyS_bpf` compares the command against14 at `ffffff800812c1ec`; commands above14 return `-22`. All 1,106 disassembled syscall instructions match the actual Image bytes at their linked offsets. This establishes binary behavior independently of merely finding an old source directory.
3. **One actual syscall replay.** A tiny static PID1 ran on that exact selected Image, using the established standalone network VM shape: one Cortex-A53 CPU,384MiB, single-thread TCG, no NIC/disks/monitor/reboot,90-second limit. It created ARRAY(4,4,31,flags0), updated/read back an entry, then issued five genuine metadata queries. Creation returned fd3/errno0; update and lookup returned0 with equal data; each info query returned `-1/errno22`. The guest powered off normally in0.466 seconds, QEMU exit0. This replay verifies the failed syscall boundary, not the full loader or Android boot.

The published `BpfSyscallWrappers.h` macro uses command15 for each of type/key/value/entries/flags and returns `-1` when the syscall fails. The qualified loader's strict legacy-kernel path checks those real values. Thus a usable map fd produces the five `-1` values and `EINVAL`, and its mismatch path returns `-ENOTUNIQ`. The final loader's installed bytes are bound to the prior genuine-loader test; independent compiler/source provenance for that executable is not claimed.
