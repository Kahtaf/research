# Independent GPIO28 port review: CHANGES REQUESTED

**P1 blocker: the new codec-private-data teardown leaves an independently registered PM caller able to dereference NULL.** Real isolated ARM64 compilation and DTB validation passed before this finding was discovered. Those successes do not approve this candidate. No further target compilation followed the finding, and no candidate source fix was made.

**P2: full reprobe leaves the analog and gate suspend flags inconsistent.** Both findings have reproducible host evidence using the actual candidate functions. Hardware, integration, full kernel, image, flash and HAL qualification remain withheld.

## Findings and smallest fixes

1. **P1 — serialize codec-private-data lifetime with the independent routing PM path.** In `candidate/.../mt_soc_codec_63xx.c`, `mt6323_codec_remove()` now calls `kfree(mCodec_data)`, sets the global pointer NULL and clears `mInitCodec` (approximately lines 3983–3989). Previously the remove function only logged and returned. `SetAnalogSuspend()` still unconditionally enters `SavePowerState()` and other analog functions that dereference that global (lines 113–121 and 166 onward). Its gate call may return `-ENODEV`, but this is ignored and does not guard the later analog access.

   The pinned BMC's separate `sound/soc/mediatek/mt_soc_audio_8163/mt_soc_pcm_routing.c` platform driver registers `mtk_routing_pm_ops_suspend` through its own `.pm` table. Codec unregister does not unregister that routing platform driver. With voice/FM/offload false, the actual callback and actual `ConditionEnterSuspend()` reach `SetAnalogSuspend(true)` after codec detach. The source-selected routing file SHA256 is `c458de71bb3c2cccd8b0d39a4c7c6e3a75f962cc8bdda44697eacca4f30bbd3a`, matching the complete BMC source manifest. This is the public pinned baseline caller, not the excluded rejected PCM patch.

   **Repro:** successful actual platform/card probe → actual codec/platform detach and managed unwind → actual routing PM suspend callback. `remote/evidence/lifetime-routing-pm-run.log` reports `runtime error: member access within null pointer of type 'struct mt6323_Codec_Data_Priv'` in the verbatim `SavePowerState()` body; UBSan exits 1 as expected. `lifetime-null-run.log` reproduces it through a direct exported-function call too. No device or real PM action occurred.

   **Smallest robust fix:** establish a common lifetime/readiness synchronization rule for codec initialization, removal and the exported analog PM entry point, and reject/no-op the analog transition when private state is absent. Hold that protection throughout access, so removal cannot free the data after a check. A bare NULL check leaves a concurrent free race. Avoid recursively taking the existing gate mutex via `p00a_gate_suspend()`. Audit other external private-state consumers before retaining the new free. Require the PM-after-detach repro to survive without touching an unowned GPIO and add a concurrent removal/PM regression case. This review changes no production source.

2. **P2 — reconcile suspend state on full reprobe.** The new gate probe initializes `p00a_gate_suspended=false`, while codec removal/probe never resets or reconciles the old global `mAnaSuspend`. The concrete sequence successful probe → `SetAnalogSuspend(true)` → full detach → full reprobe leaves `mAnaSuspend=true` and `p00a_gate_suspended=false`. Another `SetAnalogSuspend(true)` is skipped by the old flag, and actual external mixer On returns 1. `remote/evidence/lifetime-stale-suspend-run.log` records this exact synthetic software lifecycle sequence. It is not an observed system/hardware sequence.

   **Smallest fix:** initialize or preserve the analog/gate suspend state coherently under the same lifecycle synchronization, with an explicit readiness policy. Require a suspended reinitialization to keep On blocked until the intended resume transition; do not solve this by blindly clearing a live suspend interlock. Add a regression covering suspend, teardown and reprobe together. Existing host reset code sets `mAnaSuspend=false`, which concealed this case when lifetime and suspend were tested separately.

3. **API limit, not an additional candidate blocker — successful GPIO status cannot detect every MT8163 register-write failure.** Actual `mtk_gpio_set()` discards `regmap_write()` status; `mtk_pmx_gpio_set_direction()` discards it and returns zero. `mtk_pmx_gpio_request_enable()` similarly does not propagate all mux/input-enable programming failures. Actual MT8163 platform data leaves `pin_dir_grps`/`pin_dout_grps` NULL, so these paths apply even with `CONFIG_PINCTRL_MTK_NO_UPSTREAM=y`.

   `remote/evidence/mtk-boundary-run.log` demonstrates six injected register-write errors through extracted actual output/direction callback bodies: initial low, On and Off all report GPIO API success and the command cache follows that success. This supplements the original fixture's injected GPIO return errors, which test only errors that escape the lower layers. Keep the gate/cache documentation restricted to **command state after reported API success**. Stronger hardware error detection would require a separately scoped controller change and its own review; do not claim this port guarantees physical low or controller-write success.

## Ownership, lifetime and qualification boundaries

GPIO lookup validates the board, codec, explicit profile, exact one-specifier singular property, MT8163 controller, local pin and zero raw flags. It rejects plural ambiguity and propagates signed errors/defer. Managed low acquisition precedes ASoC registration; cleanup is ordered before GPIO free. The external mixer cache/error/defer/fault latch, bounded low retry, shutdown stop, release invalidation and GPIO24 backend exclusion pass the covered tests. The blocking finding concerns private analog state outside the gate's own mutex, which passing gate-only concurrency does not protect.

Dynamic GPIO numbers are resolved by the actual kernel. The fixture intentionally maps local 28 to global 71, plus namespace boundary cases. Stock observed globals 897/893 and base 869 are not embedded in the candidate. Pinctrl's MTK ops are non-strict: GPIO request ownership does not exclude every separately selected mux state. There is no added GPIO28 pull/drive/delay/pinmux setting. Requesting GPIO mode before output-low cannot prove a glitch-free transition. These remain explicit gates.

The parent receipt's local28 `spkamp-en-gpio` output-low and local24 `USB_DPN_SEL` output-high establish requested stock software ownership/idle state only. They do not identify the fitted component or prove electrical levels, active playback, safe gain/amplitude, wiring or calibration. Both existing HAL profiles still have `qualified=false`, with unchanged `routes.c` SHA256 `006c73c4d3d42f18da3f8b53fddc625a38b00b88704b93730fecb015839ebec8`.

The original BMC image remains `e9cde06e85e752aec0433ea37fa926c31b4f7a72cd55453762ec6870e5bb5bf1` and config remains `10b212cabd28aad012582e86c64695ccd450650b4e09ec8da30c21e094f377c2`.
