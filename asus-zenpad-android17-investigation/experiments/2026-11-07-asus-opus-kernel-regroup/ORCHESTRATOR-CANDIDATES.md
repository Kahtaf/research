# Independent candidate ideas while Opus reconsiders

Status: hypotheses/proposals only, no source edit/build/flash or device experiment. These are not Opus recommendations and are not hardware-qualified. Preserve the no-blind-variant stopping rule.

1. Calibrate LASTPC as an independent execution waypoint, rather than treating its arbitrary values as a crash location. The actual stock3.18 Image can execute modified bytes (UTS control passed). A deliberately identifiable stock instruction waypoint before driver/kicker initialization could test whether the stock-boot cached LASTPC follows that known address across a bounded reset. Only after a positive same-reset-path calibration would the analogous4.9 waypoint be useful. This would replace an uncalibrated clue with a discriminating channel independent of USB/SD/printk/ramconsole guards. The major unknown is capture/rearm/reset-class behavior; failure means abandon this channel. An intentional waypoint stall needs supervisedPower fallback and an exact recovery-only restore path. No assumption of automatic reset or latch origin is justified. It is not a recommendation to make arbitrary register writes.

2. A stock-calibrated reserved-RAM mailbox with the smallest early writer/stock reader. Unlike current printk, it must not depend on DT-root checks, memblock, paging, printk or USB initialization. Before building4.9 instrumentation, prove the chosen bytes survive the same recovery/reset path and are readable from stock without altering PL/LK/factory state. Header/reservation bounds/cache-clean semantics are the engineering gate; choose only an explicitly owned reservation and preserve firmware-owned data. Failure to establish the mailbox means stop this path, not keep adding guards and interpreting silence. An exact read-only snapshot of the needed public header fields could expose why the present logger refuses, without a full RAM dump.

3. A minimal driver differential, only if a calibrated PC/checkpoint actually narrows the stall to initcalls/interrupts. The previously captured4.9-looking displayIRQ PC makes display/interrupt storm a hypothesis; it does not justify declaring a display-driver bug. A targeted DT-only display disable or selected-initcall omission might be cheaper than a kernel rewrite, but must first identify dependencies and a distinct expected observation. Blind stockDT/newImage crosses can fail simply because3.18/4.9 binding ABIs differ, so negative results could be uninformative. Likewise APXGPT bus-vs13MHz mismatch is a real static bug, but higher-priority architected timer and unproved reachability make it a weak first diagnostic.

Selection principle: get one calibrated independent early execution bit, then binary-search only the narrowed stage. Avoid requiring a fully functioning new USB/MMC stack to prove that the CPU entered the kernel. Keep the proven stock hardware stack for the practical Android7 fallback.
