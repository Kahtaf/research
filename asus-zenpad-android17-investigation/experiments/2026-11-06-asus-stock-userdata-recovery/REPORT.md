# Deliberate stock userdata recovery after Android 17

**Recommendation: restore the exact stock SYSTEM and BOOT, restore the exact original recovery through a separately qualified parent-owned route, enter that recovery directly, and perform its user-supervised factory reset before normal stock boot.** This is the smallest firmware-supported candidate for discarded-data rollback. It needs no SD card, full personal-data backup, OEM ZIP installation, custom metadata writer, or newly manufactured full-size userdata image.

**This study establishes the reset’s relevant machine-code behavior, not a physically qualified rollback.** R3 remains open operationally. Two real gates remain: restoring/re-entering original p10 independently of functioning stock userdata, and demonstrating reset plus stock FDE/data startup and persistence. The current rescue does not write p10 or p20. “Original pair restored” and even the OEM screen’s “Data wipe complete” are insufficient acceptance criteria.

**p20 can remain untouched throughout the Android 17 experiment and through the SYSTEM/BOOT inverse, provided the next boot is directly into original recovery. It cannot remain byte-identical through the recommended reset.** The exact OEM reset requests a whole-p20 wipe; subsequent stock FDE initializes new metadata. For this contract, only original OEM reset and subsequent original stock crypto own those changes. This is a deliberate data-discard transition, not preservation of the old encryption state. If “preserve p20” means immutable forever, this reset route does not meet that interpretation, and no alternative stock-bootable recipe has been proved here.

## What original recovery actually does

The following are exact original-ELF observations, supplemented by bounded execution of original instructions under Unicorn. All external I/O in those tests is intercepted into synthetic memory; the real updater, recovery program main, kernel, crypto and hardware were never executed.

1. **A visible menu exists.** The device factory at `0x40c460` constructs the Device vtable resolved through `0x562890`. Its menu pointer array at `0x563020` contains “Wipe data/factory reset” at index 4. `InvokeMenuItem` at `0x40192c` maps index 4 to action 6. Actual `HandleMenuKey` instructions map volume down/up/power keycodes 114/115/116 to down/up/invoke. The menu path at `0x40d358–0x40d370` calls `0x404b54`, a tail branch to reset `0x40d7ec`. Confirmation is requested when the UI is visible; only selection 7 in the exact confirmation array is “Yes -- delete all user data”. The negative test selects No and reaches no reset effects.
2. **The reset function stages a persistent wipe request.** At `0x40d894–0x40d8a4` it requests BCB command `boot-recovery` and recovery text `recovery\n--wipe_data\n`. This means a power failure can leave a pending destructive reset. Parent must not use a persistent wipe request merely to test recovery entry.
3. **The two device hooks have no hidden factory erase.** Vtable offsets `0x48` and `0x50` both resolve to `0x401a00`, exactly `mov w0, #1; ret`. This proves these two particular PreWipeData/PostWipeData hooks are no-ops in this image. It does not certify every independently started daemon or hardware driver.
4. **Reset attempts `/data`, optional `/nvdata`, then `/cache`.** Calls occur at `0x40d8c0`, conditional `0x40d8fc`, and `0x40d920`. The exact captured recovery fstab equals the BOOT fstab and has **no `/nvdata` entry**. Normal volume loading adds `/tmp` and external-storage paths; the inspected eMMC adjustment does not add `/nvdata`. Therefore the expected successful captured-fstab branch skips it. Require the actual recovery volume table to agree; a fallback table or unexpected `/nvdata` changes the reviewed write scope and stops qualification. This distinction prevents accidentally treating `/nvdata` as `/nvram`.
5. **Formatting `/data` wipes the external FDE key location first.** At `0x407fcc–0x408028`, `format_volume` takes the absolute fstab `key_loc`, opens it `O_WRONLY|O_CREAT` (`0x41`), obtains its length, calls the wipe helper, then closes it. For this fstab the path is `.../by-name/metadata`, p20, **33,554,432 bytes**. The actual `get_file_size` branch uses `BLKGETSIZE64` (`0x80081272`). The wipe helper forms `[0, length]` and uses discard/secure-discard paths (`BLKDISCARD 0x1277`, `BLKSECDISCARD 0x127d`, dependent on device type). The executed synthetic eMMC case produced a discard request `[0, 33554432]`; a second injected size produced the matching whole length. This is not a four-byte footer operation and is not evidence of physically successful erasure or all-zero readback.
6. **It formats userdata using its own linked formatter.** `0x408128–0x40816c` calls `make_ext4fs_directory` at `0x414824`, with the userdata block path, `/data`, original SELinux handle and normal null directory. An absolute metadata path leaves length at zero, meaning use device size; the `-16384` reservation is for literal `footer`, which this fstab does not use. It then formats cache, with recovery log preservation/recreation inside cache. No full OEM update is involved.
7. **It clears/reset bookkeeping.** `/misc` maps to `.../by-name/para`, p12. The eMMC BCB writer writes the 0x440-byte structure at offset zero (`0x40e1a0` onward), both when staging and clearing the request. The additional OEM call at `0x40db7c` seeks to offset `0x800` and writes a four-byte zero stage field. That field is on **para**, not a crypto-footer proposal. `finish_recovery` also removes `/cache/recovery/command` and persists logs/locale. Do not restore a stale whole para image or hand-edit these fields as a shortcut.
8. **The success message is weak.** The reset function does not branch on the results of the erase calls or bookkeeping calls before printing completion and returning 1. The metadata wipe helper’s result is also ignored before calling the data formatter. Executed negative cases prove that failed mocked erase calls still reach “Data wipe complete”, and a failed mocked metadata discard still reaches the formatter. A metadata *open* failure does abort that format call, but the higher reset function still lacks a propagated erase-result check. Logs and actual subsequent boot/data behavior must therefore be accepted together.

The metadata path does not require a valid old FDE key to format the raw userdata device. Recovery init uses its own ramdisk and recovery fstab; it does not depend on Android 17’s `/data` directory contents. This supports leaving p20 alone until original recovery takes over. It is not permission to try normal stock boot with the stale p20/new p26 combination.

[Static checks](evidence/static-checks.json), [machine-code tests](evidence/emulation.json), and bounded named disassembly files under `evidence/` make these claims reviewable. String references were used for discovery; the reset conclusions rely on call flow, vtable resolution, arguments and executed original instruction slices.

## Filesystem and FDE findings

The actual stock formatter’s initialization arithmetic was executed for the real p26 length and a smaller synthetic length, without generating an image. For p26 it selects 4,096-byte blocks, 256-byte inodes, 2,766,422 blocks (11,331,264,512 filesystem bytes), 32,768 blocks/group, 8,144 inodes/group, 692,240 inodes and 32,768 journal blocks. The last 3,584 partition bytes are outside the 4 KiB filesystem. Its feature fields are:

- compat `0x1c`: journal, extended attributes, resize inode;
- incompat `0x42`: filetype, extents;
- ro-compat `0x13`: sparse superblocks, large files, group descriptor checksums.

This agrees with the captured [AOSP7 formatter reference](https://android.googlesource.com/platform/system/extras/+/android-7.0.0_r1/ext4_utils/make_ext4fs.c), but the evidence for these values is the OEM binary execution. The normal recovery formatter supplies the OEM SELinux context handle; a generic host formatter does not reproduce that integration merely by matching flags.

The existing A17 image has compat/incompat/ro-compat `0x2c / 0x42 / 0x73`. It replaces resize-inode with directory indexing and adds dir_nlink/extra_isize. The published ASUS 3.18 `ext4.h` masks are incompat `0x183d6` and ro-compat `0x77f`; its `super.c:2787` rejects unsupported incompat bits for any mount and unsupported ro-compat bits for writable mounts. Both images pass those source-level subset checks; two unknown-feature negative controls fail as intended. Thus it would be wrong to assert that this A17 image is inherently unmountable on 3.18 just because it was qualified on 4.9. It would also be wrong to claim a real 3.18 mount/e2fsck/stock boot from that subset check. [Filesystem evidence](evidence/filesystem.json) records the precise limits.

**A stock-compatible ext4 recipe alone is insufficient.** A plain filesystem, crypto metadata, stock vold/Keymaster, SELinux labeling, init service ordering and framework state must agree. The stock fstab uses `forceencrypt=.../metadata`; the exact stock SYSTEM includes `vold.rc` and `vdc.rc`. The latter runs `cryptfs mountdefaultencrypted` for `defaultcrypto` and `cryptfs enablecrypto inplace default noui` for `encrypt`. The exact stock init contains the corresponding action-dispatch branches and the real post-fs-data/framework triggers. Selected original vold disassembly shows its external-footer handling, bad-magic branch and encryption failure behavior. This matches the general legacy [AOSP full-disk-encryption design](https://source.android.com/docs/security/features/encryption/full-disk), rather than modern metadata-encryption assumptions.

The prior uncertainty about missing OEM vold/service inputs is narrowed: these exact files are now extracted and pinned. Original vold `0x75de0–0x75eac` reads `ro.vold.wipe_on_crypt_fail` with default `0`, compares against `1`, and conditionally requests `--wipe_data\n--reason=cryptfs_enable_internal\n`. Its runtime property value remains unproved; absence from inspected props does not establish the effective value. **Do not rely on a failed stock boot to trigger automatic reset.** The deliberate OEM menu reset removes this dependency, but subsequent original stock encryption still needs physical acceptance.

No independent clean-stock userdata image is delivered or approved. Matching the OEM formatter’s fields could be a future bounded filesystem experiment; it would still need coordinated metadata initialization and stock crypto acceptance, and offers no smaller qualified recovery route here. The full 11 GB personal-data backup/upload alternative is unnecessary for the user’s discard-data goal.

## USB, entry and write-scope contract

Exact recovery `default.prop` is a user build: `ro.debuggable=0`, `ro.secure=1`, `ro.adb.secure=1`. Its adbd service is disabled by default and the normal init start trigger requires `ro.debuggable=1`. The MTK recovery init configures MTP `0e8d:2008` and charger-mode behavior; the debug-only ADB configuration uses `0e8d:201c`. The menu’s “Apply update from ADB” enters the recovery binary’s `--adbd` sideload path. **Sideload is not evidence of a general shell, root, rescue protocol, or p10 write capability.** No sideload or SD is needed for the selected local factory-reset menu.

The visible-menu key behavior is proved in code. The actual bootloader button chord, “No command” menu reveal, screen operation and return route are **not** established by that test. Existing diagnostic records explicitly leave recovery entry and locked fastboot boot/flash availability as physical gates. A generic ASUS phone reset web page is not model-specific proof; no unverified key sequence is prescribed here. Parent must qualify entry on the actual tablet without choosing wipe or applying a package.

## Ordered recovery contract — parent executes only after its physical gates

1. **Before any p26 destruction:** retain the completed public preservation receipt and all private local payloads; retain verified cloud-independent original SYSTEM/BOOT/recovery. Establish actual user presence, power and a qualified entry/fallback route. Elapsed 23:03 UTC does not establish presence. Verify original recovery menu access, navigation and cancellation before relying on it. Existing FRP remains preserved; any stock setup account challenge belongs to the user, not a bypass procedure.
2. **Resolve the p10 circular dependency:** identify and qualify the existing parent-owned method that can write/read-back original recovery while stock userdata is unusable. A route requiring booted/rooted stock Android after the inverse is circular. The original narrow rescue cannot restore p10, and stock recovery sideload is not that writer. This study supplies no new block writer or relaxed policy. If no independent p10 route exists, stop before five-role installation: the proposed recovery contract is incomplete.
3. **On an explicit rollback decision:** stop install work, establish actual idle/no concurrent writer, and reconcile the **original SYSTEM role 0**, then complete its original-source transfer and whole verification/commit. Use the existing qualified source/protocol; lost receipts mean UNKNOWN, not automatic retry. Do not alter p20 or write a second userdata recipe.
4. **Restore original BOOT role 1 only after original SYSTEM is verified.** Verify/commit its whole image. This stage is solely the SYSTEM/BOOT inverse. Do not normal-boot stock as a test of the new p26/stale p20 pair.
5. **After transactions are complete and idle, restore original p10 through the separately qualified route.** Independently verify all 16,740,352 bytes against the original recovery hash. Its access and return behavior must not require working stock userdata. This is external to rescue roles 0/1 and changes the recovery pin, so no old rescue transaction may continue afterward.
6. **Enter original recovery directly.** Verify original image identity/provenance and expected volume/alias table. No pending update request, unexpected nvdata entry, fallback layout or unexplained reset target is acceptable. Choose the visible “Wipe data/factory reset” and its explicit affirmative item under user supervision. This is the first planned p20 change. Original recovery owns the whole metadata discard, p26/cache formats and para bookkeeping; do not hand-replay those writes.
7. **Inspect actual reset evidence before accepting success.** Review the full displayed/viewable recovery log for metadata open/discard, make_ext4fs, unmount/mount, data/cache and BCB errors. Do not accept the completion string by itself. Verify no repeating wipe/update request remains when returning to normal boot. If any result is uncertain, retain logs, stop and let parent decide recovery; no automatic format/reboot loop or fallback full updater.
8. **Boot original Android 7 and qualify fresh userdata.** Require actual normal framework/setup or launcher operation, no encryption/decryption-error loop, real writable `/data`, completed expected stock FDE state, and Enforcing. Through parent’s authorized observation path, check the effective crypto properties and backing/mount state rather than synthesizing ready flags. Create a small non-private persistent setting/file, perform one deliberate normal reboot, and verify it survives with normal boot/data operation. User-visible setup alone is weaker than this two-boot persistence/crypto acceptance.
9. **Close rollback only after factory-state acceptance.** Parent compares the current factory-state results to its retained preservation records and handles any selective factory-file restoration using its own reviewed process. No bulk copying old Android `/data`, stale encryption metadata, or historical factory revision by default. Retain all original/current backups until this acceptance completes. Record “stock data recovery accepted” separately from “stock pair restored.”

## Smallest useful qualification and remaining gate

**Non-destructive prequalification:** on the present stock device, parent demonstrates original recovery entry, expected menu/key operation, the actual fstab/aliases, log visibility, cancel, and normal return. This tests the human/UI route without erasing data and establishes what evidence is obtainable without shell/SD. Separately qualify the p10 restoration mechanism before p26 depends on it.

**Smallest destructive qualification:** one supervised factory reset using the exact original recovery with original SYSTEM/BOOT, followed by stock encryption/startup and one additional normal reboot with a tiny persistence sentinel. It exercises the real p20/data/cache/para operations and the weak-success-message failure boundary. Current stock userdata is a valid baseline for this test, but success there does **not** claim the exact post-A17 transition was exercised.

**Exact post-A17 acceptance:** after a parent-authorized genuine A17 five-role installation has actually written p26, follow steps 3–9 as a deliberate rollback rehearsal. This is the direct proof of the requested transition. It does not require a second data image or 11 GB backup, but it is destructive and remains parent/user-supervised work. Do not violate SYSTEM-before-DATA-before-install-BOOT to create a special data-only trial through the existing five-role protocol. This report does not authorize or arm that installation or pretend the test has occurred.

Offline evidence makes the OEM-reset strategy credible and precisely scoped. It cannot remove the physical p10-entry, discard/format durability, stock crypto and factory-restoration acceptance gates. If parent requires demonstrated post-A17 rollback before its first full installation, that prerequisite is still unsatisfied; an untested plan must not be relabeled as a proven inverse.
