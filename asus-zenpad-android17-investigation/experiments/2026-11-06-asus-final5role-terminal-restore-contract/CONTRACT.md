# Exact final five-role integration contract

The minimal target-source change is **one shared exact-five-role manifest predicate, used at both terminal entry gates**, replacing the daemon's count-only two-role check and the helper's exact two-role check in a new final-install fork. Generate its digest only from the actual admitted five-role manifest. Keep `verify_image(0)` and `verify_image(1)` before exec and again inside the helper. Regenerate core, helper and external full-p10 bindings for the resulting container. No new target opcode, general p10 writer, DATA rollback role or p20 writer is needed. A separate mandatory policy correction grants only daemon DATA access as specified below; the frozen policy cannot provision DATA.

The review-only [delta](proposal/terminal-profile.patch.txt) changes `handoff.h`, changes `p10_restore.c`, and adds `terminal_profile.h`. It expects a parent-generated `terminal_manifest_binding.h` defining exactly `static const unsigned char terminal_manifest_sha[32]` with the real manifest SHA256 bytes. That generated header is deliberately absent. No zero digest, fixture digest, string placeholder, default profile, count-range predicate or runtime hash override is supplied. This is a source proposal, not a buildable or deployable candidate.

## Parent-supplied admission records: nothing executable yet

The current remote adapter admits only fixed stock SYSTEM and pristine DATA remotely, and fixed original SYSTEM/BOOT locally. Unknown install SYSTEM/BOOT are intentionally UNBOUND_REFUSED. No existing review JSON, `--image-sha256`, fixture manifest, or caller path extends this authority. The following is a **proposed review record schema**, not a new runtime input accepted by existing code.

After a qualified full build, parent supplies one `FULLINSTALL_IMAGE_ADMISSION1` record with these exact required fields. Hashes mean SHA256 over the stated complete byte object, encoded as 64 lowercase hex digits. Unknown fields, missing fields, null/empty values, template text and synthetic fixture provenance fail admission. No record is delivered here.

## Acyclic final container binding

Use the existing construction; do not embed the final full-image hash into bytes that determine that hash. Parent performs these dependencies in order:

1. Actual qualified install admissions plus immutable original pair and DATA define the exact five-role manifest. Compute its digest; generate `terminal_manifest_binding.h`. It depends on install artifacts, not on rescue image/helper/core.
2. Compile the extended daemon using that binding. Assemble the deterministic gzip core with that daemon, exact final manifest, existing stock init/auth-adbd/proxy, and reviewed policy/contexts; retain the wrapped stock kernel separately. In a future fork, `assemble_core.py` selects a new fixed manifest artifact and replaces its two-role assertions with exact five-role/profile checks described above. It cannot accept an arbitrary manifest argument or just a count. Do not modify the frozen script.
3. Generate `core_binding.h` from actual core bytes: normalized 2,048-byte Android header (ramdisk length at 16–19 and ID at 576–607 zeroed), normalized 512-byte MTK ramdisk wrapper (length at 4–7 zeroed), exact wrapped kernel length/hash, exact deterministic gzip including four-byte alignment padding and its length/hash. None depends on helper bytes. Existing stock header addresses, page size 2,048 and 4 MiB ramdisk reservation stay fixed.
4. Compile the helper against both the same terminal manifest binding and the new core binding. Append only its canonical uncompressed newc member (`sbin/p10-restore`, root:root, mode 0700), with exact trailer/metadata/alignment/padding. Assemble actual Android/MTK image, derive Android SHA1 ID, and zero-pad to complete 16,740,352-byte p10. Recheck actual fit and headroom; old 1,258,748-byte headroom is not a new-image proof.
5. Compute actual helper, core, image and **whole padded p10** hashes after assembly. Generate external `generated_host_binding.py` with `PRIOR_SHA` equal to this new whole p10 and `HELPER_SHA` equal to the actual new helper; leave `ARMED=False`. No frozen 3f99… or old helper pin is reused. Corrected `host.py` behavior stays unchanged pending a separately reviewed timing revision.
6. Publish a new UNAPPROVED session receipt binding exact fields: `format=P10R1`, final5role mode/profile, `manifest_records=5`, `manifest_sha256`, `image_sha256`, `p10_full_sha256`, `image_bytes`, `p10_bytes=16740352`, `payload_sha256`, `helper_sha256`, `core_gzip_sha256`, `policy_sha256`, `contexts_sha256`, `kernel_sha256`, `ramdisk_bytes`, `reservation_headroom`, plus source/toolchain/admission/independent-parser receipt digests. Keep `armed`, `execute_approved`, `timing_qualified`, `physical_GO`, `physical_validation` false. For the normal RSC1 adapter a later separately authorized contract must bind this same exact manifest/p10; it is not created here.

The parent authenticates the **entire final image, padded p10 and RAM helper externally**. At runtime `prior_container.h` pins immutable header/wrapper/kernel/core, validates derived Android ID and every canonical capsule/padding byte, and compares the on-disk helper capsule to the already loaded read-only RAM helper. Host additionally requires returned actual whole prior digest to equal its generated final full-p10 pin before activation. The exact manifest is both inside the pinned core and checked by both terminal gates. This is an acyclic binding, not cryptographic self-authentication against malicious privileged RAM/kernel/root. Do not broaden that trust claim.

The normal daemon's runtime `recovery_ok()` still hashes the complete actual p10 for RSC1 transfers. No recovery-phase proof cache, phase-only proof, relaxed transition scan or proof-removal optimization is adopted. Recovery-phase-proof source/results were not used to construct this proposal.

## Missing inputs and real incompatibilities

Missing now: actual qualified **full** install SYSTEM/BOOT raw images' whole/chunk/source-metadata/provenance/admission records; final manifest/digest; resulting daemon/core/helper/image/full-p10 pins, fit and reproduction; final source/adapter inventory and review; physical timing/exclusivity/durability/direct-entry/fallback evidence; genuine OEM reset/stock FDE/two-boot/factory acceptance. Parent may already hold build qualification evidence, but it was not supplied here and is not inferred from build progress. No build/delegate polling occurred.

There is no logical hash-cycle blocker, and no reason for a broader p10 writer or helper policy. There are concrete acceptance incompatibilities:

- Frozen exact-two-role binding cannot authorize a five-role image. Historical fixture five-role hashes and the previous zero-record delivery are not substitutions.
- The host-overlay handoff authorizes its integration scope as STOCK-only; reuse of its receipt/deadline **semantics** is appropriate, but final5role applicability requires a new exact-profile review. This document is a proposed extension, not retrospective acceptance.
- Permanent byte identity of p20 conflicts with the selected OEM reset. p20 stays untouched through install and original SYSTEM/BOOT/p10 rollback; direct original recovery reset legitimately requests a whole 33,554,432-byte p20 wipe, then stock crypto initializes metadata. No partial-footer shortcut is justified.
- A normal stock boot with stale p20 and Android 17 p26 is not an entry route. The RAM helper closes the software p10 dependency; physically qualified direct recovery entry still must exist before relying on it.
- No-shell stock recovery is expected. Menu navigation, log access and recovery-to-normal-return evidence must be physically obtainable without assuming sideload supplies root/shell.
- OEM “Data wipe complete” ignores some erase failures. That string alone cannot close reset acceptance. Baseline stock reset success cannot close genuine post-A17 transition acceptance.
- Minimal source delta is not minimal physical requalification: changed daemon/helper/core/manifest/full image have new identities. Reusing frozen results cannot authenticate new bytes or accept new DATA/reset behavior.

Factory-private preservation, selective restoration and final factory acceptance remain parent-only. Adopt supplied public preservation acceptance without opening its private payload. All local work here is text design; there is no full-flash or physical GO.
