# Future RSC phase-bound recovery proof

Status: source-only bounded correction for independent parent review. No new recovery image, deployable binary, manifest authorization, device operation, physical qualification, timing claim, or Android17/data enablement. The existing STOCK-only candidate and all its approvals remain frozen. Host test executables are ordinary-file/socketpair fixtures only.

The proposal removes the repeated full p10 hash from each WRITE/SKIP. It retains the five existing full content proofs per image, keeps a read-only p10 descriptor for the connection, and validates that descriptor and its source/run binding on each chunk. This is justified by the fixed RAM service graph's lack of a concurrent recovery writer. It deliberately changes detection latency for an unexpected content change; it is not an inode-based content-change detector.

## The invariant, and what actually establishes it

During ordinary RSC reconciliation/writing/verification/commit, no reachable program can write recovery through an admitted path. The one reachable recovery writer replaces the ordinary daemon by `exec`, inherits the lifetime writer lock, and never returns to ordinary serving. This is a property of the exact trusted RAM image, configured services, authenticated fixed proxy, source control flow, effective policy and descriptors together. It is not established by searching globally for one SELinux type or merely holding a block FD.

The actual stock-only `core.cpio.gz` was parsed locally using the saved public newc parser. Its extracted `init.rc`, `default.prop` and `ueventd.rc` are in `context/`; the frozen core inventory is receipt-pinned. There are exactly three configured services: ueventd through the stock init symlink, `os-rescue --serve` (oneshot, root, exact domain, init-owned socket), and `rescue-proxy --adbd`. Init starts those services, initializes directories and USB/functionfs, and restores fixed labels. There is no imported init file, recovery/updater service, fstab, partition mount, shell service, boot-repair action, `exec` action, or p10 helper service. The inventory contains the fixed proxy at `/system/bin/sh`, not a general command interpreter. The separately appended capsule supplies only the fixed helper. No AOSP tree, active source/build, or device was consulted.

`proxy.c` accepts only `-c rescue-v1` under real/effective UID2000, exact shell domain, non-TTY descriptors and Enforcing. Its adbd launch path checks the fixed shell label and execs the preserved authenticated adbd. The fixed secure/nondebuggable properties, binary pins and existing authenticated-adbd boundary are adopted unchanged; no claim about exploitable bugs or arbitrary privileged code is added. Authentication/domain behavior on the physical tablet remains parent work.

The fresh read-only effective-policy query uses the locally vendored Android7 libsepol and exact frozen `restore-sepolicy`. `evidence/policy-reachability.txt` enumerates effective permissions for all six reachable actor domains (init, ueventd, adbd, shell, os_rescue, p10_restore), six relevant block types, the executable types, mutual process/FD permissions, capabilities and kernel-security permissions. It includes expanded attribute permissions and MLS evaluation through `sepol_compute_av`, rather than matching raw policy text.

* Only p10_restore has `write` to `rescue_recovery_device`. Nobody in this actor set has `write` to `rescue_disk_device` or generic `block_device`.
* Init has getattr/setattr/relabelto on the recovery and disk types. Ueventd has create/unlink/getattr/setattr. Neither has open/write on the recovery type. Their real node-creation/replacement authority is why the per-chunk descriptor/path/alias/geometry checks remain necessary. The fixed init actions do not relabel p10 to a different writable stock type or execute an updater. No configured action manufactures an alternative raw-device writer.
* Adbd/shell have no recovery/disk access. Neither can transition to, execute the helper, or ptrace the daemon/helper. Authenticated file-sync or shell requests do not introduce a block writer through the fixed labels/DAC/proxy.
* Ordinary os_rescue can write only its admitted BOOT/SYSTEM targets under the frozen policy; it can read p10/disk. `open_part(write)` rejects recovery and whole-disk writes independently of policy, and protocol target paths are fixed, never client-supplied. GPT and target descriptors prevent the ordinary target from being silently redirected onto recovery. The default policy still denies userdata.
* Only os_rescue has the process transition to p10_restore and permission to execute its entrypoint. Init has no helper service/transition; shell/adbd cannot execute it. The new daemon/helper types inherit no broad stock attributes and have no capabilities or fork grant. Existing BLKGETSIZE64-only ioctl controls are unchanged, as are policy constraints and their prior structural receipts. No block-RO setting, ioctl policy or kernel is changed.

The daemon accepts one session at a time while holding its abstract-socket writer lock for its entire lifetime. Competing daemon starts cannot bind that lock. A partial request/slow operation occupies that session; no helper request is processed alongside it. Opcode0x30 is admitted only in session IDLE; `handoff.h` then requires exactly two roles, no uncertain image, identity, and full original SYSTEM/BOOT proofs. It copies the connection/lock/listener before replacing FDs3/4/5 and execs the fixed helper. There is no fork. An exec failure exits74, never ordinary serving. The new guard is closed before this transition. The exact handoff body was tested at the mocked exec boundary: the inherited lock still excludes a second bind and the three passed descriptors survive exec. Five-role and uncertain requests refuse.

The unchanged helper independently validates UID/domain/peer/inherited lock, RAM-only state, its exact two-role stock manifest, original pair and fixed prior container. It opens p10 writable only in its fixed restore transaction, uses O_EXCL, retains full prefix/prior-suffix transition proofs, fsync/readback and final full proof, then permanently serves only terminal observation. It retains the lock in terminal UNKNOWN/DONE/SKIPPED; there is no route back to RSC, staging or another attempt. Those helper bodies/bytes are untouched, not optimized or newly physically qualified here. Death or exec failure does not produce success; the host's unknown outcome remains unknown, and the configured daemon is oneshot.

This excludes arbitrary external root, a hostile kernel, unreviewed service/binary/policy changes, hardware faults as an exclusion guarantee, and additional storage writers outside the fixed parent-owned image boundary. An inode/FD cannot prove block content immutability against those actors. Adding a vendor updater, generic shell, new service or writable alias invalidates this proof. The smallest necessary design in that case is to remove/serialize that actual writer under the same lifetime lock and exclusive phase handoff, then re-establish the effective reachable graph; otherwise retain per-chunk content proofs. Merely setting a trusted/readiness boolean cannot fix it.

## Source change and consistency semantics

`future-source.patch` changes only `rescue.c` and adds `recovery_phase.h`. Copies of common.h, sha256.h and handoff.h remain exact. All original-source receipts, helper, policy, contexts, manifest, image and host flags are preserved in `evidence/frozen-input-receipts.json`; `baseline/` matches the specified original sources exactly. Proposed source hashes are in `evidence/proposed-source-receipts.json`.

A guard lives on one `session()` stack, starts with fd=-1, and opens/validates p10 read-only at initial reconciliation. It snapshots the descriptor's device/inode/rdev/mode/owner and exact manifest ID/p10 pin, then hashes all recovery bytes through that held FD. The descriptor stays open until success, any exit/error, or helper handoff. No guard is global, persisted in the journal, reconstructed from STATUS, or reused on reconnect. The unchanged manifest digest binds the CID/GPT/image geometry/chunk source digests. The source arrays are loaded once before serving, and are not mutable through the protocol.

Activation requires another full proof and binds the selected image plus the freshly generated reconciliation token. Chunk checks require that proved activation and exact image/token/manifest/pin, and re-run recovery descriptor/node/label/geometry/aliases/holders/mount checks. Identity/Enforcing/CID/GPT and the held target FD checks remain in their existing per-chunk path. Production open flags and validation bodies are unchanged. A descriptor or source/run mismatch closes and invalidates the guard; there is no lazy fallback to opening a replacement descriptor or marking it ready. A same-byte recovery-node replacement that old code could reopen is now refused within the connection. Opening a fresh connection still requires all content proofs and a fresh token.

All five full p10 proofs remain: before reconciliation scan, after that scan, at activation, after whole target readback before VERIFIED, and at commit before the commit receipt. Each full proof validates the same p10 FD before and after hashing. Per-chunk proof removal is the only content-I/O reduction. There is no cached original-pair/prerequisite proof or cached target/source hash. WRITE payload hashing, current-chunk read for WRITE and SKIP, false-SKIP rejection, write/fsync/readback, whole-image target verification, explicit inverse constraints and order are unchanged.

Failure behavior is explicit:

| Event | Result |
| --- | --- |
| Wrong p10 before reconciliation/activation, short recovery read, open/validation failure | Refuse; no new mutation. Existing uncertainty is preserved. |
| Changed recovery node/alias, held FD replacement/closure, changed geometry/holders/mounts/CID/GPT/Enforcing | Per-chunk guards refuse before the next target operation; close guard at session end. No reopen bypass. |
| Unexpected same-node p10 content change in WRITING | May acknowledge later valid target chunks; full recovery proof before VERIFIED refuses if changed bytes persist. No whole-image/commit success. This is a deliberate boundary detection model. |
| Change after VERIFIED but before commit | Commit full proof refuses; already written image remains uncertain. |
| Corrupt source data, false SKIP, partial write, failed fsync/readback, target replacement | Existing stop/freeze/uncertain behavior remains. No retry or automatic inverse. |
| Broken/partial frame, disconnect, lost chunk ack | Session ends, closes guard, preserves uncertain image/pin. New session must explicitly reconcile actual bytes with a fresh token. |
| UNCERTAIN or VERIFIED journal publication/fsync loss | No successful progression; target may already have changed, so uncertainty is retained. Journal remains tmpfs, not restart-durable. |
| Failed commit send | Frozen/uncertain. |
| Kernel accepts commit send but host loses receipt/publication | Daemon may be IDLE; host MUST retain UNKNOWN. Guard lifetime/state is not a durable host receipt. Corrected comment documents this existing distinction. |
| Helper transition/terminal uncertainty | Guard closes; ordinary writer cannot continue. Unchanged helper owns lock and fixed transition proofs. No rollback/reboot/restart invented. |

A retained witness intentionally mutates p10 outside the invariant after one acknowledged chunk. Baseline rejects the next chunk; revised source can acknowledge the remaining valid target chunks, then refuses full verification. A mutation between VERIFIED and commit also refuses commit. This is not represented as identical instantaneous detection. A transient change restored before all observations need not be detected by either sampling design; neither design is a continuous hardware content monitor. If a parent requires immediate detection of an untrusted concurrent content writer, this patch is insufficient and per-chunk hashing is itself only sampling; a real exclusion/change-notification design is needed. No arbitrary-root/kernel protection is claimed.

## Host evidence and arithmetic

Final local Linux tests use the existing local audit image, network disabled, nonroot UID501, all capabilities dropped, no-new-privileges, read-only container root, only this spike mounted, no devices added, CPU0 only, one-CPU quota, memory/swap each capped at 1GiB, and serial compilers/tests. `evidence/local-container-command.json` pins the image ID and exact command; cgroup limit/peak receipts are separate. GCC ASan/UBSan/bounds and halt-on-error are used for the actual C bodies. These fixtures do not qualify Android block syscalls, SELinux domains, OEM nodes or physical recovery.

The ordinary-file/socketpair suite includes the exact complete `rescue.c` and production SHA256; only RESCUE_TEST's existing regular-file backend and explicit syscall fault/tracing boundaries are used. Both baseline and proposed source run the same tests. The small geometry has four SYSTEM chunks and 8KiB recovery: baseline counts nine p10 opens/full hashes, revised counts one open/five full hashes for either WRITE or SKIP. Actual nonmatching WRITE tests exercise write/fsync/readback. Direct guard tests cover changed manifest, pin, image, token, closed descriptor and dup2 descriptor replacement. Handoff tests execute the unchanged handoff body up to a mocked exec boundary. Sanitizers report no failure in final passing runs.

The exact full-geometry accounting fixture retains all production session/body/control-flow and geometry/manifest parsing. It substitutes explicitly symbolic length hashes and pread results, and scripted framed input/output; it is a call-count model, never a safety or cryptographic test. Generated files omit only the first `#include "common.h"` to permit those boundary adapters. Every remaining production body byte is verified against its source; the receipts identify both versions. The five-role symbolic manifest is modeling only, not a genuine image/profile or deployable authorization. Sparse ordinary files provide sizes, while payload pread never reads them. No actual 241GB read occurs.

For both opcode4 and opcode7, the model executes each actual full-geometry chunk and counts p10 opens, reads, full hashes, all hash calls and hashed bytes. WRITE inputs in this model match the symbolic current chunk and take verified-SKIP; actual changed WRITE behavior is covered by the separate real-SHA small fixture. Source chunk hashes remain accounted for on opcode4. Complete results are in `evidence/full-geometry-counts.json`.

This is arithmetic and instrumented control-flow accounting, not storage throughput, wear, duration, power or tablet-speed evidence. Native Darwin runs and failure logs remain supplementary; final Linux cgroup receipts are authoritative.
