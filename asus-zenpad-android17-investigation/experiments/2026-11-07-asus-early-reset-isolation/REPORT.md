# Early reset isolation result

No defensible watchdog compatibility fix was established. No new image was built. The exact installed candidate already supplies the generic watchdog binding and its compiled probe stops the watchdog. A 31-second default in that driver is not an automatic 31-second boot timeout. Changing the timeout, disabling watchdog support, enabling the legacy kicker, or adding another compatible would not fix a demonstrated fault.

The useful discriminator is now narrower: determine whether the candidate reaches its retained checkpoint and whether it reaches the generic watchdog probe/stop. The observed 33.075..33.341 seconds includes the original reboot and firmware time and ends at current stock kernel startup; it is not measured 4.9 uptime. It is earlier than the inherited nominal 60-second PID1 normal reboot. This excludes attributing the return to that intended delay under the documented timing assumptions, but identifies no reset source.

## Exact candidate and compiled behavior

`evidence/offline-verification.json` was generated from the actual local candidate SHA-256 `2a0d400811292ece957bb00f632f56aef8e5967643bd5a0184c10eaeea051533`, not a template DT. Its packaged DT SHA-256 is `49ae75d4ee2e667a7242dae9d1fb659ffca7d82bda967956e8c00b14dde9d5f0`. `/soc/toprgu@10007000` has both `mediatek,mt8163-rgu` and `mediatek,mt6589-wdt`; address/size are `0x10007000/0x1000`; absent status means enabled. Its entire watchdog node equals the independently compiled DT's node.

`drivers/watchdog/mtk_wdt.c:592..595` matches `mediatek,mt6589-wdt`. The register identity agrees with the parent's live stock facts: stock's node has only `mediatek,mt8163-rgu`, and binds its vendor `mtk-wdt` platform driver. A shared driver name does not imply the same OF matching table or startup implementation. Missing stock `/sys/class/watchdog` is consistent with its vendor path and does not demonstrate a candidate binding failure.

Generic `mtk_wdt.c:435..445` can return before mapping; after successful mapping it initializes the device and stops it at lines 484..489 for this exact non-DOUGLAS/non-GIZA config. The exact original vmlinux matches the original build receipt; disassembly proves call `ffffff80088093a8 -> ffffff8008808cf4 <mtk_wdt_stop>`. Stop reads MODE, clears bit 0, adds key `0x22000000`, and writes MODE. This occurs before watchdog registration. Its log message “Watchdog enabled” later in probe does not describe this branch accurately.

Timeout defaults to 31 seconds, range 1..31. `set_timeout` writes `(seconds << 11) | 8` to LENGTH and reloads with `0x1971`; comments describe 512-tick units from a nominal 32 KiHz source. Stock source uses the same encoding and its exact compiled probe selects 30 seconds. There is no DT clocks property or Linux clock-rate acquisition in this generic driver; an actual independent hardware clock rate was not measured. Start enables MODE bits 0, 2, 3, 6 and sets polarity/IRQ level. It is called through watchdog operations, explicit proc control or resume of an active/running watchdog, not this config's probe branch. Probe does also configure thermal/scpsys reset requests; their runtime assertion was not observed.

`CONFIG_MTK_WD_KICKER=y` does not produce a kicker here. Both parent Makefile gates require disabled `CONFIG_MTK_WATCHDOG` before descending into `mediatek/wdk`. Exact ELF symbols contain the generic implementation but lack `mtk_wdt_restart`, `wd_api_init`, `get_wd_api`, `wdt_arch_reset`, and the checked legacy kicker entry points. Legacy kicker source calls `mtk_wdt_restart(WD_TYPE_NORMAL)`; its API calls legacy mode/timeout functions. Those calls and dummy branches are not linked into this image. There is no evidence for an executing weak legacy reload stub. The linked weak `rtc_mark_wdt_aee` is an unrelated RTC marker, not a keepalive.

If firmware leaves a watchdog running and Linux stalls before successful generic probe/stop, a timeout remains possible. Source and ELF cannot establish that the candidate reached the stop or that the hardware accepted it. The observed wall-clock interval is compatible with that possibility, not proof of it. A successful stop also does not exclude a separate thermal/PMIC reset or an explicit software reset.

## Matching stock reset semantics

The exact shipped stock kernel, extracted offline from the preserved recovery binary, contains the vendor `mtk_wdt_probe` at `ffffffc000800638`: it selects 30, writes reload `0x1971`, then enables dual/IRQ/external/reset operation. Its API/kicker implementation is present. This corroborates the preserved 3.18 source rather than inferring stock behavior from configuration.

The stock `mt_boot_reason.h` enum assigns 3 to `BR_WDT` and 4 to `BR_WDT_BY_PASS_PWK`. Exact stock `dt_get_boot_reason` consumes the cmdline digit; 4 is a boot-reason category, not the raw RGU STATUS register. Exact stock `arch_reset` and `wdt_arch_reset` show deliberate normal reboot sets the bypass bit and writes software-reset key `0x1209` at RGU offset `0x14`. Source explicitly describes MODE bit 4 as the bypass-power-key flag. Thus watchdog-reset machinery is shared by deliberate software resets. `boot_reason=4` cannot establish an unexpected timeout. No equivalence with the independently reported Android property `sys.boot.reason=0` was established. The exact LK binary's strings alone were not treated as decoded classification control flow.

## Retained writer can refuse before publishing

Candidate `asus_retained_trace.c:167..175` requires a complete existing Linux console layout: exact `sz_buffer`, `off_linux`, `off_console`, `sz_console`, PL/LK relationships and valid ring counters. These are stronger prerequisites than merely possessing the firmware signature/reservation. Header and early-map failures go directly to `unmap` at line 176/183; those paths are silent. The warning at line 214 only covers the earlier `refuse` path.

Matching stock initializer computes/writes Linux offsets and sizes itself after saving the old buffer; its machine code was already corroborated in the retained-trace spike. Consequently valid firmware-owned PL/LK state does not by itself prove the candidate's Linux-field predicates. Strict guards can reject a pre-Linux state lacking those initialized fields. Whether this actual firmware handoff presents that state is unobserved. No invented header, guard relaxation, or inference of paging failure is justified. Stock text retention proves its own writer/reader path, not guard passage in the candidate.
