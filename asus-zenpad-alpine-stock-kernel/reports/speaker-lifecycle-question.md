## Proposed single route to review

Use a small lifecycle observer attached to the OWNED PulseAudio Unix server and exact asus_dl1_rw sink. Not an alternative decoder/backend and not a kernel patch. It reacts to sink state plus a bounded periodic health check:

1. Cold/desktop start: both gates must already be Off, gain/class read and privately saved, acquire exclusive ownership; start observer only after exact PulseAudio serial sink validation. No amp writes merely for startup. Firefox starts afterwards.
2. RUNNING only: validate the exact PulseAudio identity, module config and live PCM RW/S16_LE/48k/stereo owned by its Tgid. Then apply known0Db/CLASSAB and Speaker→Ext, with immediate readback. This RUNNING condition must be source-verified to mean actual output demand, not a monitor/pactl client or merely a corked stream.
3. IDLE/SUSPENDED, server loss, validation failure or ordinary stop: ExtOff→SpeakerOff, verify Off, then restore saved class/gain. Never wait the5s idle timeout to turn off the amps.
4. Ordinary desktop exit: stop observer/confirm amps Off before terminating owned PulseAudio. Service stop must retain the ALSA fallback guard. No restart loop or unknown-state mutation.
5. Independent cleanup: a separate bounded guardian owns an episode lease containing exact controller PID/start/boot and preimage, with monotonic heartbeat expiry. On controller death/stale lease it forces gate shutdown in reverse order and only then restores class/gain. Need a precise minimal lease protocol that cannot let a stale guardian switch off a later owner's route, or leave amps on while the parent hangs. A temporary prototype episode is hard-capped (for example6s); do not turn it into a permanent unqualified daemon.

Please challenge this ONE design from pinned PulseAudio17 and exact original vendor source. If an existing standard component can supply these ordered transitions with equal ownership/failure semantics, prefer that only if source proves it; do not survey speculative variants. State whether sink RUNNING is the right trigger, event subscription/requery race handling, practical startup/stop ordering, independent-guardian ownership/lease details and which failure paths are truly coverable in userspace. If a safe minimal controller cannot be justified, identify the smallest concrete blocker rather than suggesting amp-on forever.
